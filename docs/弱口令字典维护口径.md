# 弱口令字典维护口径

内置字典是「这个端口有没有低级错误」的第一轮检查，不是穷举。这份文档定的是：**什么条目能进来、
进来放哪一档、什么时候复核、改完怎么验**。代码在 `scanner/credscan_dict.go`。

## 一、为什么不做全量口令库

两件事必须分开：

- **内置档**：出厂/默认口令，随平台发布，任何任务都用它。它的存在是「这个服务装完没改密码」。
- **导入档**：操作员按目标显式导入的字典（`cred_tasks.dict_profile`）。它的存在是「这个目标我怀疑
  有特定口令」。

把全量库塞进内置档有两个后果，都不是技术问题：跑一遍全网端口等于替操作员决定了「打多大」，
出了事没人说得清这是谁的意图；而内置档越大，预算越容易在真正该试的那几条之前耗尽。

所以默认路径永远是精简的。要大字典，走导入档，并且是一次显式的动作。

## 二、分档与版本

内置档分两档，尝试顺序固定为 **core 全量 → vendor 全量**：

| 档 | key | 收什么 | 判断标准 |
| :-- | :-- | :-- | :-- |
| 通用 | `core` | 空口令、`root:root`、`admin:admin` 这类与厂商无关的组合 | 任何一台设备出厂都可能长这样 |
| 厂商/设备 | `vendor` | MSSQL `sa`、Jenkins/JBoss 控制台、svnserve、RouterOS、SNMP 的 `public/private/community` | 只对特定协议有意义，但对那个协议必须靠前 |

顺序不是分组并发：它决定「最先试出什么」，也决定预算耗尽时牺牲谁。分档只是为了给新条目一个
明确的位置，并让界面能说清这一版覆盖到哪（`GET /api/credscan/protocols` 的 `builtin_dict`）。

**版本号**：`CredBuiltinDictVersion`，格式 `YYYY.MM`，同月内二次调整加 `.1`（例如 `2026.11.1`）。
它表示**内容版本**，不是程序版本：条目变了就跟着变，界面靠它回答「这次跑的是哪一版字典」。

## 三、加一条的门槛

三条都要满足，缺一条就不加：

1. **能说出出处**：哪个产品、哪个版本、出厂或安装脚本默认就是它。注释里写清楚。
   「网上见过有人这么用」不算——那类条目的误报成本（多打一次、可能触发锁定）高于命中收益。
2. **能在 lab 里复现**：用 `tools/e2e/credscan-lab/` 起真服务，命中路径走通一次。
   起不了真服务的协议（已在 1.6.0 砍掉的 Oracle/WebLogic/WinRM/CobaltStrike 那一类）不加新条目。
3. **形状对**：SNMP 这类「凭据就是口令」的协议，条目必须无用户名；写进 vendor 档而不是 core。

删条目同样要理由：只有当它被证明确实不存在于任何出厂配置，或者会造成稳定的误报（例如某些服务
把空口令解释为「匿名」而不是「无口令」），才删。删的时候同步升版本号。

## 四、复核节奏

| 时机 | 做什么 |
| :-- | :-- |
| 每季度一次 | 检查 vendor 档：新出的产品默认口令、已停产品的条目是否还值得留 |
| 新增协议时 | 该协议至少一条出厂口令进 vendor 档，并补一条 lab 用例 |
| 每次发版前 | `go test ./scanner -run TestCredBuiltinDict` + `go test ./scanner -run TestCredOrder` |
| 收到误报时 | 先查是不是「空凭据/匿名语义」导致，再决定改字典还是改适配器判据 |

字典复核不阻塞发版：它影响命中率，不影响结论正确性。但**改了字典就要升版本号**，否则报告里
「用的是哪一版」说不清。

## 五、改完怎么验

```bash
cd scanner 所在目录
go test ./scanner -run 'TestCredBuiltinDict|TestCredOrder' -count=1
```

四条测试分别锁：分档合计 = 实际条目数、尝试顺序 = core→vendor、无重复条目、SNMP 条目是无用户名的
纯口令。想验真命中，用 lab：

```bash
tools/e2e/credscan-lab/docker-labs.sh up     # 或 six-pack.sh 的六条
JW_CRED_LAB=1 JW_CRED_LAB_MANIFEST=/tmp/jw-cred-lab-6/lab.json \
  go test ./scanner -run TestCredLabProtocols -count=1 -v
```

**只加条目不跑真机，不算验证过**：进程内协议桩拿不到「服务端认不认这组口令」的结论，
1.6.0 的教训就是桩与实现按同一份错误理解写，测试一直是绿的（见 `进度手册` §5.9）。

## 六、与协议定向排序的关系

`OrderCredentialsForProtocol` 只做一件事：把某协议最该先试的条目提到前面（目前只有 SNMP 的
community），**只重排、不增删**。它不能用来「临时屏蔽」某条口令——少一条等于在报告里声称
测过一组其实没测的口令。
