+ netns 内网段 10.99.0.0/24 里的 Ubuntu-2、Ubuntu-3，覆盖：无 LLM 扫描 + 基线、LLM 深挖 + java-chains、

keyword DSN 四种全过；疑似抖动包 `-count=6` 复跑；浏览器 e2e 57 项；截图必须人看。

**弱口令检测一档第二批真机验证（2026-11-05，B3b）**：验证台从 16 条扩到 **27 条 / 21 个协议**，
在 Web Basic（Apache Basic）、WebDAV（Apache mod_dav）、Tomcat 管理台（tomcat9-admin + manager-gui）、
Elasticsearch 8（X-Pack Basic，HTTP 层关 TLS）、Memcached（无认证）、Zookeeper（四字命令）之外，
又加了 dovecot（POP3/IMAP + 993/995 隐式 TLS）、postfix + dovecot SASL（SMTP AUTH，2525）、
slapd（LDAP 389 + LDAPS 636，自签证书、简单 bind）、TigerVNC（VncAuth，5901，禁用黑名单）。
每个仍走命中 + 拒绝两条路径；`JW_CRED_LAB=1 go test ./scanner -run TestCred` 全绿（223s）。
真机抓到的问题：dovecot passwd-file 必须 root:dovecot 0640（0600 会让认证「临时失败」）、
SMTP 的 SASL 应答要 2 秒以上（6 秒首字节耐心不够）、VNC 服务端在连续失败后会进入黑名单
（验证时用 -BlacklistThreshold 1000）、Xtigervnc 的 WSL WDDM 警告会让包装脚本误判启动失败（直接起 Xtigervnc）。
**浏览器端到端**（隔离 dev 实例 + Playwright，2026-11-05）：字典导入 → 新建任务（目标 `host:8092`、
协议 http-basic、字典 lab）→ 运行完成显示「命中 1」→ 详情显示账号与依据 → 「原始报文」弹窗含凭据行与
HTTP 报文 → 外部观察：命中已写资产/发现/凭据库且状态未变。**无 JS 错误**；截图见 `browser-check/shots/credscan-*.png`。

**平台自测**：1.3.1 之前把平台自身当目标扫过一轮，并针对登录入口做定向验证，产出即 1.3.1 的登录防护项。

**弱口令检测一档协议真机验证（2026-11-05，B3a）**：`tools/e2e/credscan-lab/up.sh` 在宿主机与 Ubuntu-1
上摆出真守护进程，`JW_CRED_LAB=1 go test ./scanner -run TestCred -count=1`（156s，引擎单测与真机用例
一起跑）用被测适配器逐个打。**14/14 通过**，每个协议各含命中与拒绝两条路径：Redis（`requirepass` +
未开认证）、PostgreSQL（scram-sha-256 / md5 / trust 三档认证，同一实例且**服务端开着 TLS**，
三档都在通道内完成认证）、MongoDB（scram-sha-256 / scram-sha-1）、MySQL（Ubuntu-1 的
caching_sha2_password 与切换到 mysql_native_password，服务端 advertise `CLIENT_SSL` 后同样走 TLS）、
SSH（Ubuntu-1:2201）、Socks5（danted username 认证 + `ssh -D` 无认证代理）、FTP（vsftpd + PAM 本地账号）、
Telnet（netkit telnetd）。TLS 不只是「连上了」：清单给这些用例写了 `expect_tls`，用例断言结果的 `TLS`
标记必须为真、且**证据文本必须说明字节是通道内明文**——悄悄退回明文是一种不会反映在 outcome 上的错误，
只能这样拦。也正是在这里露出第 12 条缺陷（`Identify` 没跟着升 TLS 而 `Try` 升了：同一个协议的两条代码
路径对同一件事给出不同答案）。两条守卫：**8 个适配器逐个按在 HTTP 端口上无一确认成功**（真机版的
「不靠端口猜协议」）、**空凭据不判成命中**（Redis 未开认证与 PG trust 除外——那两条的空口令本身就是结论）。
过程中被真服务逼出的 12 条线上缺陷见 §5.4；口令全部现场生成、只存 `/tmp/jw-cred-lab/lab.json`（600），
`down.sh` 负责删临时容器/临时用户、恢复 `/etc/vsftpd.conf` 并清掉清单——**验证台自身不留残留，
三台靶机上的渗透载荷不在它的清理范围内**。

### E4：exec() 语境的命令编码助手（真实进程等价核验）

交付的是三层：`scanner/exec.go`（把一条命令行编成 shell / argv / 单串三种语境各自的形式，并判定
「这条需不需要 shell」）、`server/exec_form.go`（`POST /api/deep/exec-form`，纯静态换算，不发包、
不接触目标）、工作台终端的「exec() 语境形式」对话框（`_components/exec-form-dialog.tsx`）。顺带把
同类缺陷清掉一处：`JINGWEI_WEBCRACK_PYTHON` 原先按空白切分（路径含空格直接被拒），现在走同一套
命令行切分，引号算数。

**验收用的是真实进程，不是字符串相等**：`scanner/exec_test.go` 对每条命令跑三条路——
(a) `sh -c 原命令`、(b) `exec.Command(argv[0], argv[1:]...)`（无解释器）、
(c) 把单串形式**按 Java 的空白规则切碎**后同样直接 exec——三条输出必须一致且包含预期内容；
解释器各跑 `/bin/sh`（本机是 dash）与 `/bin/bash` 一遍。另钉一条反面证据：含管道的命令原样按空白
切碎后的输出**必须**与 shell 语境不同，否则这个用例就只是在自我确认。

| 命令 | 判定 | 单串语境给出的形式 |
| :--- | :--- | :--- |
| `cat /etc/passwd \| grep root` | 需要 shell（管道） | `/bin/sh -c cat${IFS}/etc/passwd\|grep${IFS}root` |
| `cat "/tmp/a b"` | **不需要** shell（引号只是分组） | `bash -c cat${IFS}"/tmp/a"$'\x20'"b"`（标注目标要有 bash） |
| `netstat -antp \| head -20` | 需要 shell（管道） | `/bin/sh -c netstat${IFS}-antp\|head${IFS}-20` |
| `ls /etc/p*.conf` | 需要 shell（通配符） | `/bin/sh -c ls${IFS}/etc/p*.conf` |
| `echo $HOME/x y` | 需要 shell（变量展开） | `/bin/sh -c echo${IFS}$HOME/x${IFS}y` |
| `cat /etc/shadow 2>/dev/null \| head` | 需要 shell（管道、重定向） | **拒绝**：重定向造不出解析期词边界，指向 argv 语境 |
| `for i in 1 2; do id; done` | 需要 shell | **拒绝**：控制结构，指向 argv 语境 |
| `dir /s /b "C:\Program Files"` | Windows | 只给 `cmd.exe /c <整条命令>` 的 argv，不给单串形式 |

这一轮把编码从「打印整条命令再把空白换掉」推翻重写，原因记在 §5.7 第 5 条——那三种写法都会
**静默**改变语义，而且改完仍然返回 0，正是这个功能要防的东西。

界面核验（2026-11-06，隔离实例 `jw-e4`：独立库 `jingwei_e4` + 独立容器 127.0.0.1:9797 + 只指向
不存在地址的一条壳记录，换算不接触任何目标；Playwright 走真实接口与真实构建的前端）：
首启初始化那道滑块是用**平台自己的求解器**过的（`captcha.SolveSlider`，第一次就通过，没有读服务端
答案、没有绕过校验），会话令牌只注入浏览器上下文。8 项全过：

| 输入 | 界面上看到 |
| :--- | :--- |
| `cat /etc/passwd \| grep root` | 「需要 shell 才解释得了」+ 构件「管道 \|」；切碎对照 5 段；argv `["/bin/sh","-c",…]`；单串 `/bin/sh -c cat${IFS}/etc/passwd\|grep${IFS}root` |
| `cat "/tmp/a b"` | 「不需要 shell：参数可以直接是 argv」+ argv `["cat","/tmp/a b"]`；单串落在 `bash -c` 并挂出「要求目标上有 bash」的标注 |
| `cat /etc/shadow 2>/dev/null \| head` | 不给单串形式，写明「重定向造不出解析期词边界」并指向 argv 语境 |
| 关闭对话框 | 终端仍可用，输入不被吞；整轮无 `pageerror` |

唯一的 console 报错是脚本第二次用同一个 URL 建壳记录时后端回的 400（同址只留一条，正是产品行为），

### G4：维持痕迹矩阵（报告自动列出留下什么、验证到什么程度）

交付：`db/intranet_artifact_traces.go`（17 种手段 × 痕迹/验证/残留三栏，单一来源）、

矩阵想替代的是「靠经验写清理说明」这件事，所以口径全部写死在渲染里：

| 结论 | 成立条件 |
| :--- | :--- |
| 已验证清除 | 台账里有独立验证命令，且验证输出带 `JW_ARTIFACT_GONE`（撤销命令的退出码不算证据） |
| 未配置验证命令，无法复核 | 只跑了撤销命令——**这一条是特意保留的难看结论**，写成「已清除」就是假话 |
| 撤销失败，仍在目标上 | 撤销或验证明确失败，附复核原文第一行 |
| 仍在维持中 | 本轮没有执行撤销（例如未开启自动删除 webshell） |
| 本轮未执行撤销 | 预览（dry-run） |

「撤销之后仍然存在的痕迹」逐条列在表后（认证日志、cron/服务/TaskScheduler 事件日志、WMI 存储库、
注册表 hive 时间戳、访问日志、mtime、堆内存痕迹等）——这些不是没清干净，而是当前权限与技术下清不掉
或不该动的东西；账外残留（G1）另起一节并写明「平台没有部署它们，也就无法声称已经清除」；本轮没有
登记任何维持手段时那一节写「没有执行残留扫描」而不是「没发现」。

核验（三层，全部跑过）：

- **覆盖**：17 种 kind 逐一要求痕迹、验证、残留三栏非空；新增 kind 只加常量不加档案 → 用例红。
  半持久化两种形态额外要求验证方式同时覆盖「标记块」与「载荷文件」（只验一个会留下悬空引用或
  一个可重新指向的块）。
- **渲染**：五列表格每行分隔符数量固定、单元内竖线转义、`Unknown` 与 `LedgerExternal` 分别成节、
  空台账时不出现「已扫描的类别里没有发现」这种把没做写成没发现的句子。
- **端到端**：在桩 webshell 通道上真部署 cron 与 SSH 授权公钥 → 真撤销 → 真复核。矩阵把有验证命令的
  cron 记为「已验证清除」，把**故意抽掉验证命令**的公钥记为「无法复核」；同时直接读桩 crontab 确认
  信使行确实消失；dry-run 那一轮不允许出现任何「已验证清除」。

未做真机对照的部分如实记下：痕迹与残留的描述来自实现本身与常规取证常识，没有逐条在真实
Windows/Linux 主机的 EDR 视图里核验（手头没有 Windows 靶机，三台边界/内网靶机按约定不清理且当前
不可用）。所以矩阵只说「留下什么、验证到什么程度」，不写「检测不到」——它不是规避承诺。

- 正向：`NEXT_PUBLIC_MOCK=1 npm run build:static` → 本地静态服务 → 巡检 **42 个页面全部渲染、

### C3：子域名枚举（字典 + 公开接口 + 解析 IP + 联动端口探测）

交付：`scanner/subdomain.go`（引擎）、`scanner/testdata/crtsh-sample.json`（线上真实响应形态的固定样本）、
`db/subdomain.go` + `subdomain_tasks` / `subdomain_results` 两张表、`server/subdomain.go`（任务、执行、
资产落库、端口探测、报告 Markdown）、`function/subdomains` 页面与侧栏入口。

引擎的三条判据（缺一条结果就不可信，全部有用例）：

| 判据 | 做法 | 不做的后果 |
| :--- | :--- | :--- |
| 泛解析检测 | 每个根先拿随机名问一次；答得出来就记下答复指纹，与基线一致的命中不计入发现、单独计数 | 字典爆破每一条都「命中」，一次能造出几千条假子域名且全指向同一个 IP |
| 未判定 ≠ 不存在 | NXDOMAIN 才是「不存在」；超时/SERVFAIL/连不上解析器一律计入未判定并留样本名字 | 报告把「没问到」写成「没有别的子域名」 |
| 查询预算 | 候选总数与实际问出的次数都记；到点停止并写明停在哪一段 | 悄悄截断的覆盖面是假的（与漏扫丢最新模板同一类错误） |

两处口径是设计时定下来的，都值得记一笔：

- **公开接口默认关闭，且地址不可填**。查 crt.sh 会把客户的根域名发给第三方——授权清单管不住这条外发，
  所以必须显式勾选，界面与报告都写明「发出去了什么」。地址固定为 crt.sh：能填 URL 的枚举接口就是 SSRF 跳板；
  顺带加了跨主机重定向拒绝。
- **范围闸问两次，第二次只跳一步**。根域名不在授权清单里 → 整单拒绝、一次查询都不发；解析出的 IP 不在授权范围内
  （客户常只写域名）→ **只跳过端口探测、保留名字**，原因写进日志与摘要。全单失败会让人以为这轮什么都没查到，
  静默跳过会让人以为查过了，两种都比少探一段危险。

核验（本机，全程不出网、不打任何真实客户域名）：

- **真链路**：一次性实例 + 一次性库 + 本机 hosts（`jwlab.test` 及三个子名，含一条 AAAA-only）+ 本机 18080 监听。
  结果：4 条命中、6 行资产（A/CNAME/AAAA 各成一行，与 `(domain, record_type)` 唯一键一致）、
  2 个 IP 送去探测、1 个开放端口与 1 个 Web 服务写回 IP 资产、`nope` 正确判为不存在；
  范围外的根域名建任务直接 400 并点名授权清单；报告 Markdown 表头、来源中文、结论一句都在。
- **真 DNS**：`miekg/dns` 在 127.0.0.1 上起一个只监听回环的 DNS 服务器，让 `net.Resolver` 从它那里拿答复——
  这一层专门覆盖假解析器测不到的部分：A/AAAA/CNAME 的真实分类、IPv6 是否保留、NXDOMAIN 与「问不出来」的分别。
  泛解析两种形态各验一次：只有 A 泛解析时，AAAA 那条真记录必须留下；A 与 AAAA 都泛解析时一条发现都不留。
- **crt.sh**：线上抓了一次真实响应做固定样本（字段名与 `name_value` 多行写法只有真数据能证明）；
  实网另跑两次，一次客户端超时、一次 502，两种失败都只记「公开接口失败 1 次，那部分覆盖面缺失」，其余来源照跑。
- **界面**：mock 静态导出 43 个页面全渲染、0 脚本错误（新页面在 CI 巡检里就有覆盖），截图确认为真实界面。

已知边界（不做，写清楚）：泛解析检测走本机配置的解析器，缓存型解析器与权威 NS 的答复可能不同，
要精确到权威 NS 需要可配置 DNS 服务器，这一版没做；`SubdomainRootsFromTargets` 的注册域判断按标签数粗判
（`shop.corp.example.org` 取 `corp.example.org`），宁可少切一段也不把别人的域名当成目标；
公开接口只有 crt.sh 一家，其它来源按未知来源记为「跳过」而不是静默丢弃。

交付：`scanner/endpoint.go`（签名表 + 识别 + 补丁基线，纯函数）、`server/intranet_endpoint.go`

| 口径 | 做法 | 不这样做的后果 |

| 读不到 ≠ 没有 | 命令失败、权限不足、**只有表头**都算空输入，结论是「不做判断」 | 「Access is denied」被读成「查过了、没有防护」 |
| 基线未命中 ≠ 漏洞 | 每条通告列 KB **集合**；累计更新会取代早期编号，未命中写 medium「待确认」 | 一台打满补丁的机器被报出四条「高危缺失补丁」 |

（`endpoint_security` 字段），只回看 status=done 的运行记录——失败的那次不能被当成「查过了」。

核验：scanner 10 例（tasklist CSV / sc query / linux ps 三种格式、无子串误报、未登记待确认、
空输入、基线命中与未命中、累计更新取代、不完整输入）；server 6 例（台账写入与重跑去重、
三种不写台账的情况、回看只认成功运行）；报告模板分支用**服务层真实生成的标题**测，
防止被前面的泛化分支截走。Windows 真机验证记在待办（与 F3 的 Windows 脚本同一笔账）：
本机没有 Windows 靶机，`tasklist`/`sc query`/`Get-HotFix` 的真实输出形态只按公开文档构造了用例。

0 脚本错误，内网页截图确认为真实界面；新展示块只在有真实运行数据时出现，mock 无此数据，
其正确性由类型守卫与服务层用例覆盖。四组合全量测试（并行/串行 × URI/keyword）全绿。

### B4：二档协议显式降级进协议目录（「暂不支持」逐项可见）

降级决定早已记在规划表：8 个二档协议（MSSQL、SMB、WinRM/WMI、Oracle Listener、RouterOS、
CobaltStrike 面板、Jenkins、SVN）本版不做适配器——每种握手都要真服务对照（NTLM 要域控或
Samba 对照、SOAP 要看厂商 WSDL、私有握手没有标准），本周期拿不到可复现的验证环境。
这一交付把「降级」从文档里的一句话变成逐项可见的事实：

- **目录**：`credUnsupportedProtocols` 从布尔集合改为「名字 → 原因」映射，逐项登记降级原因；
  `CredProtocolCatalog` 给每个不支持项带 `note` 与展示端口（二档端口进默认端口表只供目录展示，
  创建阶段就拒，引擎永远走不到）。
- **拒绝**：创建 API 与 agent 工具当场带原因拒绝（不发起任何连接）；引擎若收到这类端点，
  登记的原因原样写进结果行（「暂不支持：<原因>；未发起连接」）。

  challenge/digest」反推确认。命中：`( success ( ) ) ( success ( <uuid> … ) )`；拒绝：

| RDP | 真 xrdp 0.10（`security_layer=negotiate`） | `inconclusive`，`RDP X.224 CC（flags=1, selectedProtocol=0）` | **没有 deny 路径** |

RDP 那条要单独说清楚：xrdp 只允许 TLS，协商应答里 `flags=0x01` 就是「拒绝标准安全层」，
**口令一个字节都没发出去**。这时写 `deny` 是伪造结论（等于声称「这组口令被排除了」），
只能落 `inconclusive` 并在 Reason 里写明「只接受 TLS/CredSSP，未提交凭据」。识别仍算成立——
`flags≠0` 的公理是「这确实是 RDP」，不是「协商成功」；初版实现只认 `02 00 08 00`，把 xrdp
直接判成「不是 RDP」（§5.9 第 7 条）。

真机暴露并修掉的问题全部记在 §5.9；其中 Jenkins 那条会 **100% 误报**（任何口令都判命中），
桩一直是绿的。这是这一批最值钱的产出，也是「不假验证」这条纪律的实证。

### 5.4 弱口令检测一档协议在真线上暴露的缺陷（2026-11-05，B3a）

这一批的价值不在「协议接上了」，而在**每一条都是真守护进程逼出来的**。自写 Go 靶子和自写适配器
可能错得一模一样（两边都按同一份 RFC 的同一处误读实现，测试照样绿），所以下面这些只有在线上的
才会现形。验证台与复跑方式见 `tools/e2e/credscan-lab/README.md`。

| 协议 | 线上表现 | 根因与修法 |
| :--- | :--- | :--- |
| PostgreSQL | `08P01 malformed SCRAM message` | `SASLInitialResponse` 的**长度字段含结尾 NUL**，而 client-final 那串**不能带 NUL**——两处语义相反。靠 python/socat 代理抓一段真 libpq 握手逐字节对比定位 |
| MongoDB | `no such command: '$db'` | OP_MSG 的文档是**有序**的：命令名必须在第一、`$db` 必须在最后。改成显式排序的 `mongoCommand(w, db, kv...)`，不再靠 map 遍历 |
| MongoDB | SCRAM-SHA-1 恒 `Authentication failed`（SHA-256 却对） | 错猜过四种（MD5 组 HMAC、MD5 串当 Mac、"MongoDB Client Key" 标签、salt 取后 10 字节），全部否掉后**拿 mongod 存的 `storedKey` 反推**证实：机制就是标准 HMAC-SHA-1 + PBKDF2 取 20 字节 + 全量 salt，只有**口令输入**换成 `hex(md5(user + ":mongo:" + password))`；另外 gs2 头 `n,,` 不能进 auth-message。这条结论写进代码注释，下次不必再猜 |
| MySQL | `1156 Got packets out of order` | 包序号不能由本地计数器走：必须**从刚读到的那个包的 seq 推导**，只有客户端连续发两包时才自增（认证切换与快速/完整认证通道两种顺序都落在这个规则里） |
| Telnet | 明明登录成功却判 `inconclusive` | 读循环在第一个空闲间隙就停，且把「输入用户名后」与「输入口令后」两段回显**拼接**——于是早先那个 `Password:` 被当成第二次提示＝失败。拆成 `telnetReadUntil` + 分开保存 before/after；IAC 协商要剥掉并对 `WILL` 回 `DONT`（回错码位 0xfc/0xfe 也是这一批修掉的） |
| FTP | vsftpd 被当成「连不上」 | banner 因为服务端反查 DNS **延迟到连接后好几秒**才来。新增 `credFirstReadWait`（首字节等 6s）并让所有读截止不超过本次尝试的 deadline——不能改成无限等，那会把预算吃掉 |
| FTP | `421 too many connections` 被判成 `locked` | 「账号锁定」是很重的结论，进了报告就会让人以为目标配了锁定策略。连接数超限属**没测出来**，归 `inconclusive`；从锁定文本里摘掉 `connection limit exceeded` / `too many authentication measures`，同时造一条真 `account locked` 用例，保证锁定这条路仍然有效 |
| Redis | Redis 8 的未开认证措辞不匹配 | `AUTH <password> called without any password configured` 与旧版不同，匹配放宽 |
| SSH | deny 行没有任何字节，且证据里的复现命令照做也得不一样结论 | ① `readLine` 改为**也记录读到的字节**（服务端版本行是 KEX 之前唯一的明文）；② KEX 之后全是密文，裸 socket 复现命令复现不出认证判定，所以 SSH 自己写 `EvidenceText` 讲清这一点——**宁可解释「为什么不能逐字节复现」，也不给一条假的复现命令** |
| Socks5 | 只支持无认证的代理被判成「不是 SOCKS5」 | 问候必须**同时**提供 `00`（无认证）与 `02`（用户名/口令），只提供一种是错的；另外 dante 认证失败时回 `01 01`（继续子协商）而不是直接断连接，RFC 1929 的这一段要按回包分支处理 |
| PostgreSQL | 服务端开了 TLS 后，`Identify` 报 `unexpected EOF`，而 `Try` 却能认证成功 | `Identify` 只发了 SSLRequest 收到 `S`，却**没有真的升 TLS** 就发 StartupMessage——PG 在 `'S'` 之后只接受加密通道上的启动包，明文发过去直接被断。两条代码路径对同一件事处理方式不同，正是「认证能过所以协议确认也一定能过」这个假设的漏洞；补齐 TLS 后三档认证全在通道内跑通，`res.TLS` 也才有真机依据 |
| FTP / Telnet | 用户名或口令里带 CR/LF 等于**往服务端塞第二条命令** | `credWire.writeLine` 直接拒绝含 CR/LF 的行，把这条约束放在公共层而不是每个适配器里各写一遍 |

顺带把三条引擎层的约定也定下来了（都是接适配器时才发现的）：**每次尝试的超时归引擎**
（`context.WithTimeout(runCtx, credAttemptTimeout)`，适配器不许自定全局超时）；**emit 由引擎串行化**
（原来把并发责任推给调用方，八个适配器一起接就会撞）；**单测桩要用自己的协议名**——真适配器一旦
注册 `redis`/`ssh`/`mysql`，桩再叫同名就会被 `RegisterCredAdapter` 判重复 panic，这恰好也证明注册表
的重复保护是有效的。


### 5.5 一档第二批的降级决定（2026-11-05，B3b）

这一轮把 **Web Basic / WebDAV / Tomcat 管理台 / Elasticsearch / Memcached / Zookeeper**
六个协议做完并各自在真服务上验了命中与拒绝两条路径；**SMTP / POP3 / IMAP（含 SSL）、
LDAP / LDAPS、SNMP、VNC** 没有实现，按规划表「做不动的降级进三档并如实标注」的口径处理：

- 它们在协议目录（`GET /api/credscan/protocols`）里 `supported=false`，页面禁用；
  创建任务时直接 400「该协议暂不支持」，**不建任务、不发连接、不产出结果行**。
- 为什么不先写一个「大概能用」的实现：这几种协议的认证都不是「发个口令看状态码」——
  LDAP 要 BER 编码与 bind 语义、SNMP 要 ASN.1 且「凭据」是 community、VNC 是 DES 挑战应答、
  邮件是 SASL 多轮。没有真服务对照时，自写实现与自写靶子会一起错（B3a 的十二条线上缺陷
  已经证明过这一点），而一个错的适配器比「暂不支持」更坏：它会产出看起来可信的假结论。
- **进展（2026-11-05）**：邮件三兄弟、LDAP/LDAPS、VNC 已按「先摆真服务再写适配器」的口径补齐并验证；
  **只剩 SNMP 仍在三档**——它走 UDP，且 community 错误时设备静默丢弃，本版「明确拒绝 vs 没测出来」
  的判定边界无法在 UDP 上成立；要做得先给传输层加 UDP 与独立的「无应答」语义。
- 后续口径：先给每种协议在 `credscan-lab` 里摆出真守护进程与命中/拒绝两条用例，再写适配器；
  在完成之前继续留在三档并保持可见。

顺带的两个设计决定：**内置字典的第一条是空凭据**——Redis 未开认证、Memcached、Zookeeper
这类根本没有认证的服务，只有空口令这一组能命中；**「服务器未启用认证」只对空凭据记命中**，
非空口令一律记 `deny` 并写明「不构成可用凭据」，避免把任意口令都报成弱口令。HTTP 家族在
带凭据成功后还会再做一次**无凭据对照**：同一路径不带凭据也成功，说明资源本来就不设防，
那一行只能记 deny，不能把「资源开放」算到这组口令头上。

### 5.6 统一测试阶段暴露的缺陷（2026-11-05，1.5.0 收尾）

发版前把「四组合全量测试 + 真机基线 + 浏览器逐页验证」一次跑完，查出 **13 条**——其中 8 条是
「代码写完、单测全绿、产品里却用不了」这一类，只有把请求真打到产品上才会露出来。
第 1-11 条当场修掉；第 12、14 条（编号按追加顺序）是**后来补的**——第 12 条曾作为待办记进 §5.2，
经负责人要求继续修之后按新增范围实现并真机复验；第 13 条由 I3 自检脚本首跑发现。

1. **提交里少了功能代码**：`20ac370` 的说明写着「撤离后台账外残留扫描与客户交付版报告」，树里

   提交。按那条提交检出，两个功能根本不存在。补提交 `0f5c44d`。**同类问题本月第二次**（上一次是
   `db/credscan*.go`）——提交后必须 `git show --stat` 核对文件清单，光看 `git status` 干净没用。
2. **F3/F4 的接口从未注册路由**：`authorizations` / `intranet/scripts` 两组 handler 在、前端在、
   单测全绿（用例直接调 handler），界面上点就是 404。补注册，并加 `server/routes_wired_test.go`：
   从 `web/src/lib/api.ts` 认出前端会调的 236 个路径，逐个用 `ServeMux.Handler` 问「注册了没有」

   从来没被执行过。
4. **`TEXT[]` 数组列在 pgx 文本协议下读不回 `[]string`**（驱动给回的是 `{a,b}` 字面量字符串）。
   改成与仓库其它数组列一致的 JSONB；迁移时 Postgres 会按**旧类型**校验新默认值，必须先
   `DROP DEFAULT` 再 `ALTER TYPE`，否则报「default cannot be cast automatically」。同一条 schema
   里还踩过第二个坑：`information_schema.columns` 不按 schema 过滤会把**别个测试库的旧表**也算进来，
   条件必须加 `table_schema = current_schema()`。
5. **测试进程里泄漏的投递循环**：八处用例用 `New(context.Background(), …)` 造 Server，`New` 起的
   通知投递循环就活到整个测试进程结束，而 `step()` 每 tick 遍历库里**所有**启用渠道——它抢走了通知
   用例刚分派出的投递行，失败长这样：「假接收端没有收到任何请求」。红绿取决于用例执行顺序（只有

6. **`go test ./...` 的 TMPDIR 落在 770M tmpfs 上**：并行组合把测试二进制写进 `/run/user/0` 时空间
   不足，报出来是 `fork/exec …/*.test: no such file or directory`，以及一批 php 用例「服务没起来」
   的假故障。测试脚本固定 `TMPDIR=/root/tmp`（磁盘）。
7. **php -S 端口先查后用**：`freeLocalPort` 空出的端口下一秒可能被别的测试包占走，php 报地址占用后

8. **夹具过期**：memcached 已经有适配器，创建任务时应当放行，用例还把它当「没有适配器的协议」断言
   被拒——换成 snmp（在默认端口表里、确实没有适配器）。
9. **扫描超时的文案会说谎**：超时那一轮报「已保留 0 条 POC 结果、0 条发现（含应用层探测、弱口令与

### 5.7 1.6.0 第一批（D4/D5/F6）自查出的问题（2026-11-06）

这两项是「上一轮已经写出来、但结论不可信」的账，都在合并前被推翻重写，记下来是因为它们的失败方式
不是崩溃，而是**看起来一切正常**。

1. **性能基线量的不是它声称的东西**。旧 `scan-bench.sh` 在**运行中的生产容器**里 `docker exec` 跑 nuclei，
   输出重定向到 `/dev/null`：模板加载失败、进程退出码非 0 都不影响它给出一个数；夹具只提供 `/p0…/p3`
   四个路径而模板请求 `/a /b /c`，于是所有请求都是 404、匹配器全不命中；nuclei 默认还开着请求聚类，
   「1000 模板」根本不等于一千次请求。报出来的 100ms 级数字量的是「nuclei 启动一次 + 一堆 404」。
   后果比数字不准更糟：那组数被写进 CHANGELOG 用来论证「分片代价可忽略」。**处理**：撤销全部旧结论，
   基准改到一次性隔离容器（无外网、限 CPU/内存/PID、只读、禁止拉镜像、清空环境变量），并逐格断言
   退出码＝0、夹具收到的请求集合恰好＝模板数×目标数、JSONL 的 (模板, 命中地址) 不重不漏、
   `-disable-clustering` 固定带上；基线文件带环境指纹，指纹变了就拒绝比对。新基线 18 格 × 3 次采样见
   `tools/e2e/README.md`。

2. **续扫的草稿会把「没扫」说成「扫过」**。逐条自查出的洞：
   - 分片只按「模板序号」划分，一片里混着多个目标 → 中断后整片重跑，但重跑时前几个目标的结果被唯一键吃掉、
     `persistResults` 返回的计数少算，汇总数字与台账对不上；
   - 计划只存模板 ID，不存内容摘要 → 中断期间有人改了 POC，续扫会拿旧的「已完成」进度配新的模板，
     报出来的覆盖面是假的；
   - `FinishScanShard` 全部是 `_ = err` → 检查点没写进库而任务报 done；
   - 结果落库在 ctx 取消时被 `persistResults` 的 `ctx.Err()` 直接 break → nuclei 已经产出的命中整批消失；
   - 深挖与 SQL/XSS 专项基线用「本轮内存里的结果」→ 续扫时前面几片是上次跑的，那些命中根本不在内存里，
     首轮扫出的高危漏洞永远排不上深挖；草稿还把「续扫不重跑专项基线」写成结论，而实际上首轮没跑到那一步；
   - `resume_requested` 一进续扫就清 → 再失败时认不出这是一次续扫；`RequestScanResume` 只看 `plan <> '{}'`
     → 中断在深挖阶段的任务也会被排队；重启恢复文案对所有中断任务一律写「可续扫」。
   **处理**：计划钉住模板 ID＋内容摘要＋目标顺序＋分片参数＋阶段；分片改成「模板段 × 目标组」并把目标
   写进进度行；写库/记进度任一失败立即停手且不报 done；阶段边界 `poc → postprocess → done` 只在 poc 可续；
   收尾命中改为**从库里按 nuclei 事件形状恢复**（排除目录枚举行与深挖回填行）；汇总数字按库内实际行数重算；
   每一片执行前重问资产禁令与客户授权；重跑（`QueueScanTask`）先锁行确认可重排再清产出并重置计划与分片行。
   接口层补了准入判断（进行中/已完成/无检查点/阶段不对/目标已被移出授权，各自给出能看懂的原因）。

3. **准入检查用了 30 秒前的授权缓存**：`newGuardTargetPolicy` 有进程级缓存，续扫最常见的动作是
   「刚补完授权就点续扫」，用缓存版本会误拒。准入路径改为现场读清单。

4. **日志把手写的代理说成「平台登记的隧道」**。F6 的身份判定复用了 `intranetTunnelIdentity`，而那个函数
   为了把目标解析到隧道另一头，**只要主机不是本机就返回「是隧道」**——它是解析器，不是登记表查询。
   实跑里 `socks5://172.23.0.1:18083`（本次验证临时写的代理，台账里没有这条记录）于是播报成
   「本轮走平台登记的隧道」：读的人会去台账找一条并不存在的转发，而真实原因——并发是我自己在任务里填的、
   没有任何平台侧约束——没人去查。**处理**：身份改为只查 `LiveIntranetTunnelByListen`（状态必须是部署中/
   已验证），其余端点一律记「代理端点」；用例同时钉住两种措辞与「未登记代理是否按隧道对待」开关的四种组合。
   受影响的只有那句话的措辞，预算与排队行为本来就按端点生效，不依赖身份。

5. **E4 的第一版编码会静默改变语义，而且改完照样返回 0**。第一版思路是「用解析器把整条命令规范化
   打印，再按引号状态把空白换掉」，看着等价，实跑（真实进程比对输出，不是断言字符串）抓到三处：
   - **语句分隔**：Minify 打印出来的分隔是换行，一律换成 `${IFS}` 之后
     `echo one; echo two` 变成一条命令的四个参数——输出 `one echo two`、exit 0。
   - **重定向**：`echo out 2>/dev/null` 原地换空白后，`2` 不在词首就不再是文件描述符而是普通参数，
     于是 **stdout 被整条重定向走**（输出为空、exit 0）；`tr a-z A-Z < data.txt` 反过来，`<` 的目标词
     吞掉了后面的命令，报 `cannot open data.txt tr a-z A-Z`。根因是同一件事：`${IFS}` 只在**展开时**
     拆分，而重定向要的是**解析期**的词边界，这个边界造不出来。
   - **`$'\x20'`**：本机 `/bin/sh` 是 dash，不认 ANSI-C 引用，`echo 'tab here'` 输出字面量
     `tab$\x20here` 且 exit 0——把 bash 专有写法当成了 POSIX。
   **处理**：编码改为按语法树逐层拼（参数之间 `${IFS}`、操作符与语句边界直接贴 `;`、引号内空白转
   ANSI-C），并对造不出边界的一类**明确拒绝**：重定向、循环、条件、子 shell、here-doc、命令前赋值、
   后台执行一律不给单串形式，返回原因并指向 argv 语境；用到 `$'\x20'` 时把解释器落到 bash 并在接口里
   标 `needs_bash`，让界面写明「目标上要有 bash」。三条缺陷各有用例钉住，判定方式是三种语境真跑进程
   比对输出（`/bin/sh` 与 `/bin/bash` 都跑），不是断言形式字符串。

6. **同一条缓存把「误拒」修成了「误放」，而且只有四组合测试能撞出来**。§5.7-3 把准入路径改成现场读授权
   清单，治的是「刚补完授权就点续扫被误拒」；执行期那道复核（弱口令检测发认证包之前再问一次）当时没跟着
   改，仍用进程级策略——于是方向反过来出问题：那份缓存连**「平台上还没有任何授权」这个空结果**一起缓存
   30 秒，服务刚起来的常态就是空的，操作员补完第一条授权后的半分钟内，执行器照旧认为「没有授权＝按老
   语义放行」，对着范围外主机把认证包发出去。发出去的包收不回，账号可能直接被锁，这是 fail-open。
   暴露方式很典型：`TestCredRunRefusesDeniedTargetBeforeAnyPacket` 单跑三次全绿、整包跑两轮全绿，
   只有在四种口径并行的那一格里失败（`status=done`，5.2 秒——那 5 秒就是真的在连目标）。
   **处理**：① 执行期复核与创建口统一走 `admissionPolicy()`（现场新建策略源），② 授权写入（建/删）当场
   让进程级缓存作废，agent 工具与资产禁令那几路共用它，等 30 秒同样会被误放；③ 用例里加**引信**——先跑一次
   检查把空清单缓存住，再补授权再执行，退回旧实现时用例必红（两条引信都用「把修复撤掉」实测过会失败，
   不是写完就当通过）；④ 用例目标从 `10.0.0.1:22` 换成 TEST-NET 地址：断言失效不该顺手变成一次越界攻击，
   `10.0.0.1` 在 WSL/NAT 环境里是活的网关。

7. **测试库的隔离只隔离了一半，另一半写在注释里**。`server/testmain_test.go` 的注释说「拒绝在共享表上跑」，
   实际上只挡住了自己 `OpenTestSchema` 的那些用例：这个包里一大半用例经 `NewManager()` 建服务，而它自己
   从 `JINGWEI_PG_DSN` 解析 DSN，落的是共享 `public` schema——与 `db`/`agent` 包同一批表，还夹着四条
   无条件的 `DELETE FROM authorizations`。`db` 包的授权用例（`10.0.0.0/8` 这类宽范围）此前也写在 `public`，
   于是「一个包的夹具让另一个包的范围外目标变成授权内」是随时会发生的账，只是靠 advisory lock 把两个包
   串行了才没炸。**处理**：TestMain 把 `JINGWEI_PG_DSN` 重写成钉住 `jingwei_test_server` 的形式，两条构造
   路径落到同一个 schema；`db` 的授权用例改用自己的 schema；`db.withSearchPath` 支持重写已有
   `search_path`（原来遇到已钉住 DSN 直接报错，TestMain 一改写别的用例就全崩），并把这条口径写进用例。

8. **一个 IPv6 地址会让整批端口探测静默不发生**（C3）。把解析出的 IP 送去探测时，第一版走的是
   `scanner.ParseTargets(ips)` 这条文本解析路——它只认 IPv4（`仅支持 IPv4: 2001:db8::7`），
   而 C3 的引擎**刻意保留 AAAA 记录**。结果是一个 IPv6 名字就让整批 IP 一个都探不到，
   而任务照旧 done，报告里那一栏空着——「没探」被读成「没有开放端口」，与泛解析那条是同一类错误。
   用例 `TestSubdomainRunPersistsResultsAssetsAndProbes` 第一次跑就是这么红的（`probed=[]`）。
   **处理**：探测目标直接构造 `scanner.Target{Kind: KindIP, Host: ip}`，不回文本解析路
   （`Discover` 自己用 `net.JoinHostPort` 拨号，IPv6 可用）；非法 IP 跳过并写明。
   顺带记下：`ParseTargets` 的 IPv4-only 是 C6 的账，不在这里顺手改。

9. **公开接口的超时跟着 DNS 的 3 秒默认值走，等于这一路永远失败**（C3）。crt.sh 实测 25–40 秒才回头，
   第一版共用 20 秒客户端超时，本机两次实跑一次超时一次 502——功能上线即「一直失败但看起来在用」。
   **处理**：公开接口单独 90 秒超时；失败只记「那部分覆盖面缺失」，不影响其余来源，也不假装查过。

10. **CI 巡检第一次跑就抓到我自己的构建参数错误**（I4/C3 交界）。重跑 mock 构建时漏了 `NEXT_EXPORT=1`，
    `next build` 只产出 `.next` 没写 `out/`，于是巡检打到的是上一轮**生产**导出——43 个页面里 41 个渲染成
    404 内容并带 404 资源加载错误，退出码 1。这条记在这里是因为它证明了门禁的价值：
    「构建成功」与「导出目录根本没更新」在以前是分辨不出来的。正确命令是
    `NEXT_PUBLIC_MOCK=1 npm run build:static`（`build:static` 自带 `NEXT_EXPORT=1`），CI 作业里就是这么写的。

11. **子域名枚举的台账写入失败被当成完成**（C3）。第一版把 `InsertSubdomainResults` 的错误只写进任务日志，
    然后继续走资产与探测，最后 `status=done`、摘要里写着 `found=1`——于是「报告说查到 1 条、台账一行都查不到」
    这种不一致落地，而界面上看不出任何异常。**处理**：台账写入失败直接让任务失败（`结果写入失败：…`），
    与弱口令检测「结果没落全就不能报完成」同一条规矩；引信用例把任务行删掉造成真外键违反，
    撤掉修复时用例红在 `status=done`（不是靠读代码确认的）。

12. **表头行与错误行被算成「读到过进程列表」**（F5）。第一版把每一条非空行都计为扫描行，于是
    「只有 tasklist 表头」与「ERROR: Access is denied.」两种输出都被读成「读到过、只是签名表没命中」——
    这两种情况与「真的没有防护」在报告里是完全不同的话，前者根本什么都没读到。
    **处理**：表头/标签列（Image Name、SERVICE_NAME、HotfixID 一类）与错误行（error/fatal/usage 开头、
    access is denied、not found 一类）不计为进程行；一条进程行都没读到就落空输入档，结论是「不做判断
    （不等于没有防护）」。用例把两种输出都钉成 unreadable。

13. **Windows 收集脚本里写了 POSIX 重定向**（F5）。新加的 `win-endpoint` 命令第一版写的是
    `tasklist … 2>/dev/null`——这条脚本走的是 cmd.exe，`/dev/null` 会被当成文件路径：stderr 没被吞掉，
    还可能在目标当前目录写出一个名为 `null` 的怪文件（收集脚本应当只读，这是承诺之外的写操作）。
    **处理**：改成 `2>nul`；目录用例新增一条断言——Windows 脚本的命令里不许出现 `/dev/null`，
    把这一类笔误挡在提交前。

### 5.8 1.6.0 收尾批自查出的问题（2026-11-09）

1. **svn 报文不以 `\n` 结尾，按行读会把预算耗光**：svnserve 的 S-expression 用空格分隔、
   没有结尾换行。`readLine` 的行尾判定退化成「等满首包耐心 6s」，一轮 CRAM-MD5 四条报文直接
   吃光单次尝试的 20s 上限，症状是 `dial tcp: i/o timeout`——看起来像拨号问题，其实是前一条读
   把 ctx 预算吃完了。修法：`svnReadMsg` 按静默期收一条。
2. **svnserve 的 hello 少一项就断连**：`( 2 ( caps ) <len>:<url> <len>:<client> ( ) )` 少了
   客户端标识，服务端解析后续项错位、发完 greeting 直接关连接，表现为「svnserve 不认这个协议」。
3. **svnserve 的 passwd 文件必须有 `[users]` 段**：没有它 svnserve 认为一个用户都没有，口令
   正确也 `Authentication failed`；`svn` 客户端同样连不上，所以先用客户端自证配置能省一轮排查。
4. **CRAM-MD5 的 challenge 要原样算**：HMAC 的 msg 是 `( step ( <len>:<challenge> ) )` 里的
   字节本体（**含尖括号**），去掉 `<>` 或去掉长度前缀都对不上。口径靠「抓包里的 challenge +
   digest + 已知口令」反推确认，不靠猜。
5. **`JW_PLAYWRIGHT_MODULE` 代码读了、部署没配**：`tools/envaudit` 的发版前检查当场抓住
   （`.env.example` / 两份 compose 都缺），这正是 1.4.2 那条「代码读了但部署配不上」的同型缺陷。
   已补三处登记。
6. **协议桩按明文匹配凭据会造出假失败**：MSSQL 的 Login7 用户名是 UTF-16LE、SMB 的 NTLMSSP
   Type3 也是、svnserve 的 PLAIN 是 base64。桩里写 `strings.Contains(raw,"admin")` 永远匹配
   不上，桩于是回「拒绝」，测试看起来是适配器错。修法是桩按协议真实编码构造期望值。
7. **旧断言会随实现变味**：`rdp`/`mssql`/`snmp` 从「降级协议」变成「已实现」后，三条旧用例
   仍在断言「创建即拒」。这类用例必须跟着改，否则「测试绿」会被读成「功能照旧不支持」。
   已改成用真没实现的协议名（`legacy-proto-xyz`）来钉「拒绝发生在创建阶段且声明未发起连接」。
8. **snmpd 在 WSL 里要 `-u root`**：net-snmp 默认降权到 `Debian-snmp`，在这台机器的 rootfs 上
   起不来，日志只有一句权限错误、端口根本不监听。

### 5.9 六协议真机验证暴露的缺陷（2026-11-09）

这 6 条在进程内桩下**全是绿的**，一上真服务就集中爆。逐个记，因为每一条的形态都不一样：

1. **Jenkins 会 100% 误报**：`whoAmI` 对匿名会话也回 `{"authenticated":true,"name":"anonymous"}`，
   原判据只看 `authenticated`，于是**任何口令都判命中**。这条如果漏到发版，报告会给客户交一份
   「管理员口令已被攻破」的假结论。修法：必须连 `name` 一起判，且 `name` 不能是 `anonymous`。
   ——这是本批唯一一条「错得比缺功能更危险」的缺陷。
2. **Jenkins 端点写的是 1.x 的**：`/j_acegi_security_check` 在 2.x 上一律 404（Acegi 时代早已
   换成 Spring Security）。改为先打 `/j_spring_security_check`，404 时回退老路径，并补
   `TestCredJenkinsAcegiFallback` 钉住回退分支。
3. **MSSQL 的 Login7 结构非法**（服务端回 `login packet ... structurally invalid`，Error 17832）：
   三处叠加——PreLogin 的 option offset 必须相对包体（从 16 起算，不是 0）、Login7 尾部少了
   18 字节（ClientID 6 + 三组 offset/length）、以及末尾的 `cbSSPILong` 4 字节。
   定位手段是 `tcpdump -i lo -w` + pytds 发一份真包逐字段对照，不靠猜。
4. **MSSQL 登录成功却判 inconclusive**：首个应答包是 `ENVCHANGE(0xe3)`，分类器遇到不认识的
   token 直接收工。修法：显式跳过已知的非结论 token（`0xab/0xa9/0xe3/0xe4/0xfd/0xfe/0xff/0x79`），
   并按 `status&0x01`（EOM）跨包读到结论为止（上限 8 包）。
5. **SMB2 帧结构与 NTLM 应答都不对**：① 方言数组被写进 ClientGuid 区，还声明了 3.1.1
   （3.1.1 必须带 negotiate context，否则服务端直接断）；② `MessageId` 从 1 起、缺
   `CreditCharge/CreditRequest`，Samba 日志 `bad message_id 1 (granted = 1, low = 0)`；
   ③ 第二次 `SESSION_SETUP` 没带回第一次给的 `SessionId` → `0xc000000d INVALID_PARAMETER`；
   ④ `[MS-NLMP]` 的 NTLMv2 根本没实现，NT 应答是派生占位值（`NTOWFv1 = MD4(UTF16LE(pw))`、
   `NTOWFv2 = HMAC-MD5(NTOWFv1, UTF16LE(UPPER(user)+domain))`）。前三条只影响「连不上」，
   第四条会让「正确口令也判拒绝」——四者叠加时表象只有一个：`unexpected EOF`。
6. **WildFly 的管理接口是 Digest，不是 Basic**：`/management` 带正确口令的 Basic 也是 401
   （ManagementRealm 用 HTTP Digest）。另外官方镜像的 CMD 只绑 `127.0.0.1`，端口映射进不来
   （要 `-bmanagement 0.0.0.0`），管理用户必须用 `add-user.sh -m` 建在 ManagementRealm
   （`-a` 建的是 application realm）。补了 `digestAuthorization`（RFC 7616 MD5/qop=auth）。
7. **RDP 识别只认 `02 00 08 00`**：xrdp 只允许 TLS，回的是 `flags=0x01`（协商失败），于是被
   判成「这不是 RDP」。识别标记改为「只要拿到 Negotiation Response 且 flags 任意」——
   `flags≠0` 恰恰证明对端是 RDP，只是拒绝了我们请求的安全层。`Try` 侧对应落 `inconclusive`，
   Reason 明写「未提交凭据」。
8. **桩是按错误实现写的，所以测试一直绿**（元问题，也是最该记住的一条）：`credscan_new_adapters_test.go`
   里 MSSQL 的桩接受任意 Login7、SMB 的桩不校验帧结构、Jenkins 的桩把匿名 `whoAmI` 当成功。

### 5.10 smtp-ssl 真机验证暴露的缺陷（2026-11-09）

**隐式 TLS 的四个适配器都没把通道状态写进结果**（`smtp-ssl` / `pop3-ssl` / `imap-ssl` / `ldaps`）。
`CredAttempt.TLS` 只有 MySQL 与 PostgreSQL 两个适配器会置位，邮件三兄弟与 LDAP 的 `Try` 从头到尾
没碰过它——于是结果里 `tls=false`，而 `Evidence` 的渲染逻辑据此写出两处错话：

1. 证据说明写「以上字节是明文」——实际是在 TLS 通道里；
2. 复现命令给成裸 socket（`create_connection`）——照那条命令连 465/995/993/636 **必然连不上**。

这不是「少了一个字段」，是**报告在说一件与事实相反的事**，而且看起来完全正常：outcome 是
`hit`、证据字节也有（TLS 通道内的明文），只有那句「以上是明文」是假的。报告读者照着复现失败，
只会得出「目标端口不稳定」的结论。

**为什么桩看不见**：进程内桩测的是「读到的字节能不能正确分类」，不检查 `res.TLS`；`TLS` 字段
在渲染层才被消费，而渲染层没有对着真服务跑过。真机用例加了 `expect_tls` 断言（服务端开着 TLS
时适配器必须升上去），第一次跑就是红的，红在这一条上。

修法：两个适配器的 `Try` 在握手成功后写 `res.TLS = a.tls`（邮件用 `mailCredAdapter.tls`、
LDAP 用 `ldapCredAdapter.tls`）。同时给 `smtp-ssl` 补了 lab 用例并断言 `tls=true`——只验 outcome
不验通道，这条缺陷会一直绿着。

教训与 §5.9 第 8 条同源，但方向相反：那条是「桩按错的实现写」，这条是「桩压根没检查这个字段」。
**一个适配器的结果里有几个字段被下游消费，桩就该覆盖几个字段**；只覆盖 outcome 的桩，等于只验了
一半结果。

## 6.5 A1 真机隧道的当前事实（2026-11-05）

**已修并已部署到 dev 实例**（`jingwei:dev` = `fb1796f7`，`/api/health` 报 `1.5.0-dev`）：
chisel 的 `--fingerprint auto` 与方向/`listen_side` 语义（详见 CHANGELOG Unreleased），
以及 `JINGWEI_PIVOT_SSH_PORT` 拆分。三个控制端参数已在 `.env`：`JINGWEI_PIVOT_SERVER=<内网IP>:8788`、
`JINGWEI_PIVOT_SSH_PORT=2222`、`JINGWEI_PIVOT_CHISEL_FINGERPRINT=`（留空＝不固定）。

**实验室现状**：`10.99.0.0/24` 段自建好（`jwint` 10.99.0.10 后台 :8000 与 redis、`jwcore` 10.99.0.20 :22/:80）；
访问模型是 `pivot`(uid 1002)/`www-data` 可达、root 一律 DROP，所以"只能经目标到达"成立；
控制端临时开着 2222（仅密钥、非 root、只绑内网地址）与 chisel server 8788（`--reverse`），**A1 收尾要关**。

**四条路的实测朝向（2026-11-05，同一台只有 OpenSSH 的目标 = Ubuntu-1，目的地 10.99.0.10:8000）**：
`chisel … R:<port>:socks` = 200；`ssh -N -R <port>`（不带目的地）= 200；`ssh -N -R <port>:<host>:<port>` = 读到内网主机的 SSH banner；
**`ssh -N -D <port>` 与 `ssh -N -L` = 超时**。原因是 `-D`/`-L` 的目的地由**远端**发起，这里远端就是控制端，
而控制端被段规则拦住——监听开在哪一侧不代表出口在哪一侧，此前 §6.5 记的"ssh -D/-L = 200"是把
"端口在听"当成了"流量打得通"，正是这条错记让反方向的命令一直留在选型里。`-R` 的两个前提：
控制端 sshd `GatewayPorts=clientspecified|yes`（否则拒绝在非回环上监听，现象是 ssh 活着但没监听），
以及目标到控制端免密（命令带 `BatchMode`，不同用户名会秒挂——故新增 `JINGWEI_PIVOT_SSH_USER`）。

**A1 已跑通的部分（用产品自己的 API，不是手工隧道）**：凭据入台账 → SSH 会话以 `pivot` 身份建立 →
隧道 create→probe→plan→deploy→verify 拿到 **verified**（`plan` 产出 `chisel client '…:8788'
R:0.0.0.0:11080:socks`，`listen_side=pivot`，复核 `pivot:tcp:11080` 与控制端实测一致）→
`POST /api/scans`（targets `10.99.0.0/28` + `10.99.0.20`，ports 9 个，proxy `socks5://…:11080`）**跑完**：
15 IP / 4 开放端口 / 2 服务，资产回流 6 行（`10.99.0.10` redis:6379+http-alt:8000、`10.99.0.20` ssh:22+http:80），
findings 1 条（Redis 暴露 high），自动派生的 sqlmap/dalfox 专项任务也带着同一代理打到 `http://10.99.0.10:8000/login`
并留下原始报文（200）；负向对照：容器直连 10.99.0.10:8000 超时，说明这些资产只能经隧道取得。
teardown 到 `stopped`、控制端监听消失、目标侧 pid/log 已清、`/api/managed-resources` 三条 tunnel 全 released、
`/api/managed-resources/audit` 的 `unmanaged` 为空。**A1 的 chisel 这条路到此闭环。**

过程中抓到并修掉的缺陷（都已进 CHANGELOG Unreleased）：
1. **生成 chisel / `ssh -L` 命令时丢了 `listen_host`**——chisel 因此只绑控制端回环，
   跑在另一个 netns 里的平台进程拨不到，verify 判失败（已修，`c817a94`）。
2. **ssh 变体方向反了**：选型生成 `ssh -D` / `ssh -L`，它们的目的地由控制端发起，
   对"穿透到只有目标可达的段"毫无作用；改成 `ssh -R` 后同一目标同一目的地才第一次真打通。
   教训记入开发手册：**"监听在听"不等于"流量打得通"**，隧道这类东西必须端到端取一次数据。
3. ssh 隧道缺少控制端用户名（`JINGWEI_PIVOT_SSH_USER`），跨用户名场景在 `BatchMode` 下静默秒挂。
