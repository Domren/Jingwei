**真机回归（1.4.0）**：Ubuntu-1 边界机（Apache PHP 商城 :8080 / Tomcat9 :8081 / MySQL / SSH :2201）
+ netns 内网段 10.99.0.0/24 里的 Ubuntu-2、Ubuntu-3，覆盖：无 LLM 扫描 + 基线、LLM 深挖 + java-chains、
v2 壳 + 大马 + 半持久化、内存马五类、内网横向、维持与撤离。

**工程口径**（每次发版都要重跑）：`gofmt` / `go vet` 干净；`go test ./...` 并行 + 串行 + URI DSN +
keyword DSN 四种全过；疑似抖动包 `-count=6` 复跑；浏览器 e2e 57 项；截图必须人看。

**弱口令检测一档第二批真机验证（2026-11-05，B3b）**：验证台从 16 条扩到 **27 条 / 21 个协议**，
在 Web Basic（Apache Basic）、WebDAV（Apache mod_dav）、Tomcat 管理台（tomcat9-admin + manager-gui）、
Elasticsearch 8（X-Pack Basic，HTTP 层关 TLS）、Memcached（无认证）、Zookeeper（四字命令）之外，
又加了 dovecot（POP3/IMAP + 993/995 隐式 TLS）、postfix + dovecot SASL（SMTP AUTH，2525）、
slapd（LDAP 389 + LDAPS 636，自签证书、简单 bind）、TigerVNC（VncAuth，5901，禁用黑名单）。
每个仍走命中 + 拒绝两条路径；`JW_CRED_LAB=1 go test ./scanner -run TestCred` 全绿（223s）。
真机抓到的问题：dovecot passwd-file 必须 root:dovecot 0640（0600 会让认证「临时失败」）、
SMTP 的 SASL 应答要 2 秒以上（6 秒首字节耐心不够）、VNC 服务端在连续失败后会进入黑名单
（验证时用 -BlacklistThreshold 1000）、Xtigervnc 的 WSL WDDM 警告会让包装脚本误判启动失败（直接起 Xtigervnc）。
**浏览器端到端**（隔离 dev 实例 + Playwright，2026-11-05）：字典导入 → 新建任务（目标 `host:8092`、
协议 http-basic、字典 lab）→ 运行完成显示「命中 1」→ 详情显示账号与依据 → 「原始报文」弹窗含凭据行与
HTTP 报文 → 外部观察：命中已写资产/发现/凭据库且状态未变。**无 JS 错误**；截图见 `browser-check/shots/credscan-*.png`。

**平台自测**：1.3.1 之前把平台自身当目标扫过一轮，并针对登录入口做定向验证，产出即 1.3.1 的登录防护项。

**弱口令检测一档协议真机验证（2026-11-05，B3a）**：`tools/e2e/credscan-lab/up.sh` 在宿主机与 Ubuntu-1
上摆出真守护进程，`JW_CRED_LAB=1 go test ./scanner -run TestCred -count=1`（156s，引擎单测与真机用例
一起跑）用被测适配器逐个打。**14/14 通过**，每个协议各含命中与拒绝两条路径：Redis（`requirepass` +
未开认证）、PostgreSQL（scram-sha-256 / md5 / trust 三档认证，同一实例且**服务端开着 TLS**，
三档都在通道内完成认证）、MongoDB（scram-sha-256 / scram-sha-1）、MySQL（Ubuntu-1 的
caching_sha2_password 与切换到 mysql_native_password，服务端 advertise `CLIENT_SSL` 后同样走 TLS）、
SSH（Ubuntu-1:2201）、Socks5（danted username 认证 + `ssh -D` 无认证代理）、FTP（vsftpd + PAM 本地账号）、
Telnet（netkit telnetd）。TLS 不只是「连上了」：清单给这些用例写了 `expect_tls`，用例断言结果的 `TLS`
标记必须为真、且**证据文本必须说明字节是通道内明文**——悄悄退回明文是一种不会反映在 outcome 上的错误，
只能这样拦。也正是在这里露出第 12 条缺陷（`Identify` 没跟着升 TLS 而 `Try` 升了：同一个协议的两条代码
路径对同一件事给出不同答案）。两条守卫：**8 个适配器逐个按在 HTTP 端口上无一确认成功**（真机版的
「不靠端口猜协议」）、**空凭据不判成命中**（Redis 未开认证与 PG trust 除外——那两条的空口令本身就是结论）。
过程中被真服务逼出的 12 条线上缺陷见 §5.4；口令全部现场生成、只存 `/tmp/jw-cred-lab/lab.json`（600），
`down.sh` 负责删临时容器/临时用户、恢复 `/etc/vsftpd.conf` 并清掉清单——**验证台自身不留残留，
三台靶机上的渗透载荷不在它的清理范围内**。

### 5.4 弱口令检测一档协议在真线上暴露的缺陷（2026-11-05，B3a）

这一批的价值不在「协议接上了」，而在**每一条都是真守护进程逼出来的**。自写 Go 靶子和自写适配器
可能错得一模一样（两边都按同一份 RFC 的同一处误读实现，测试照样绿），所以下面这些只有在线上的
才会现形。验证台与复跑方式见 `tools/e2e/credscan-lab/README.md`。

| 协议 | 线上表现 | 根因与修法 |
| :--- | :--- | :--- |
| PostgreSQL | `08P01 malformed SCRAM message` | `SASLInitialResponse` 的**长度字段含结尾 NUL**，而 client-final 那串**不能带 NUL**——两处语义相反。靠 python/socat 代理抓一段真 libpq 握手逐字节对比定位 |
| MongoDB | `no such command: '$db'` | OP_MSG 的文档是**有序**的：命令名必须在第一、`$db` 必须在最后。改成显式排序的 `mongoCommand(w, db, kv...)`，不再靠 map 遍历 |
| MongoDB | SCRAM-SHA-1 恒 `Authentication failed`（SHA-256 却对） | 错猜过四种（MD5 组 HMAC、MD5 串当 Mac、"MongoDB Client Key" 标签、salt 取后 10 字节），全部否掉后**拿 mongod 存的 `storedKey` 反推**证实：机制就是标准 HMAC-SHA-1 + PBKDF2 取 20 字节 + 全量 salt，只有**口令输入**换成 `hex(md5(user + ":mongo:" + password))`；另外 gs2 头 `n,,` 不能进 auth-message。这条结论写进代码注释，下次不必再猜 |
| MySQL | `1156 Got packets out of order` | 包序号不能由本地计数器走：必须**从刚读到的那个包的 seq 推导**，只有客户端连续发两包时才自增（认证切换与快速/完整认证通道两种顺序都落在这个规则里） |
| Telnet | 明明登录成功却判 `inconclusive` | 读循环在第一个空闲间隙就停，且把「输入用户名后」与「输入口令后」两段回显**拼接**——于是早先那个 `Password:` 被当成第二次提示＝失败。拆成 `telnetReadUntil` + 分开保存 before/after；IAC 协商要剥掉并对 `WILL` 回 `DONT`（回错码位 0xfc/0xfe 也是这一批修掉的） |
| FTP | vsftpd 被当成「连不上」 | banner 因为服务端反查 DNS **延迟到连接后好几秒**才来。新增 `credFirstReadWait`（首字节等 6s）并让所有读截止不超过本次尝试的 deadline——不能改成无限等，那会把预算吃掉 |
| FTP | `421 too many connections` 被判成 `locked` | 「账号锁定」是很重的结论，进了报告就会让人以为目标配了锁定策略。连接数超限属**没测出来**，归 `inconclusive`；从锁定文本里摘掉 `connection limit exceeded` / `too many authentication measures`，同时造一条真 `account locked` 用例，保证锁定这条路仍然有效 |
| Redis | Redis 8 的未开认证措辞不匹配 | `AUTH <password> called without any password configured` 与旧版不同，匹配放宽 |
| SSH | deny 行没有任何字节，且证据里的复现命令照做也得不一样结论 | ① `readLine` 改为**也记录读到的字节**（服务端版本行是 KEX 之前唯一的明文）；② KEX 之后全是密文，裸 socket 复现命令复现不出认证判定，所以 SSH 自己写 `EvidenceText` 讲清这一点——**宁可解释「为什么不能逐字节复现」，也不给一条假的复现命令** |
| Socks5 | 只支持无认证的代理被判成「不是 SOCKS5」 | 问候必须**同时**提供 `00`（无认证）与 `02`（用户名/口令），只提供一种是错的；另外 dante 认证失败时回 `01 01`（继续子协商）而不是直接断连接，RFC 1929 的这一段要按回包分支处理 |
| PostgreSQL | 服务端开了 TLS 后，`Identify` 报 `unexpected EOF`，而 `Try` 却能认证成功 | `Identify` 只发了 SSLRequest 收到 `S`，却**没有真的升 TLS** 就发 StartupMessage——PG 在 `'S'` 之后只接受加密通道上的启动包，明文发过去直接被断。两条代码路径对同一件事处理方式不同，正是「认证能过所以协议确认也一定能过」这个假设的漏洞；补齐 TLS 后三档认证全在通道内跑通，`res.TLS` 也才有真机依据 |
| FTP / Telnet | 用户名或口令里带 CR/LF 等于**往服务端塞第二条命令** | `credWire.writeLine` 直接拒绝含 CR/LF 的行，把这条约束放在公共层而不是每个适配器里各写一遍 |

顺带把三条引擎层的约定也定下来了（都是接适配器时才发现的）：**每次尝试的超时归引擎**
（`context.WithTimeout(runCtx, credAttemptTimeout)`，适配器不许自定全局超时）；**emit 由引擎串行化**
（原来把并发责任推给调用方，八个适配器一起接就会撞）；**单测桩要用自己的协议名**——真适配器一旦
注册 `redis`/`ssh`/`mysql`，桩再叫同名就会被 `RegisterCredAdapter` 判重复 panic，这恰好也证明注册表
的重复保护是有效的。


### 5.5 一档第二批的降级决定（2026-11-05，B3b）

这一轮把 **Web Basic / WebDAV / Tomcat 管理台 / Elasticsearch / Memcached / Zookeeper**
六个协议做完并各自在真服务上验了命中与拒绝两条路径；**SMTP / POP3 / IMAP（含 SSL）、
LDAP / LDAPS、SNMP、VNC** 没有实现，按规划表「做不动的降级进三档并如实标注」的口径处理：

- 它们在协议目录（`GET /api/credscan/protocols`）里 `supported=false`，页面禁用；
  创建任务时直接 400「该协议暂不支持」，**不建任务、不发连接、不产出结果行**。
- 为什么不先写一个「大概能用」的实现：这几种协议的认证都不是「发个口令看状态码」——
  LDAP 要 BER 编码与 bind 语义、SNMP 要 ASN.1 且「凭据」是 community、VNC 是 DES 挑战应答、
  邮件是 SASL 多轮。没有真服务对照时，自写实现与自写靶子会一起错（B3a 的十二条线上缺陷
  已经证明过这一点），而一个错的适配器比「暂不支持」更坏：它会产出看起来可信的假结论。
- **进展（2026-11-05）**：邮件三兄弟、LDAP/LDAPS、VNC 已按「先摆真服务再写适配器」的口径补齐并验证；
  **只剩 SNMP 仍在三档**——它走 UDP，且 community 错误时设备静默丢弃，本版「明确拒绝 vs 没测出来」
  的判定边界无法在 UDP 上成立；要做得先给传输层加 UDP 与独立的「无应答」语义。
- 后续口径：先给每种协议在 `credscan-lab` 里摆出真守护进程与命中/拒绝两条用例，再写适配器；
  在完成之前继续留在三档并保持可见。

顺带的两个设计决定：**内置字典的第一条是空凭据**——Redis 未开认证、Memcached、Zookeeper
这类根本没有认证的服务，只有空口令这一组能命中；**「服务器未启用认证」只对空凭据记命中**，
非空口令一律记 `deny` 并写明「不构成可用凭据」，避免把任意口令都报成弱口令。HTTP 家族在
带凭据成功后还会再做一次**无凭据对照**：同一路径不带凭据也成功，说明资源本来就不设防，
那一行只能记 deny，不能把「资源开放」算到这组口令头上。

## 6.5 A1 真机隧道的当前事实（2026-11-05）

**已修并已部署到 dev 实例**（`jingwei:dev` = `fb1796f7`，`/api/health` 报 `1.5.0-dev`）：
chisel 的 `--fingerprint auto` 与方向/`listen_side` 语义（详见 CHANGELOG Unreleased），
以及 `JINGWEI_PIVOT_SSH_PORT` 拆分。三个控制端参数已在 `.env`：`JINGWEI_PIVOT_SERVER=<内网IP>:8788`、
`JINGWEI_PIVOT_SSH_PORT=2222`、`JINGWEI_PIVOT_CHISEL_FINGERPRINT=`（留空＝不固定）。

**实验室现状**：`10.99.0.0/24` 段自建好（`jwint` 10.99.0.10 后台 :8000 与 redis、`jwcore` 10.99.0.20 :22/:80）；
访问模型是 `pivot`(uid 1002)/`www-data` 可达、root 一律 DROP，所以"只能经目标到达"成立；
控制端临时开着 2222（仅密钥、非 root、只绑内网地址）与 chisel server 8788（`--reverse`），**A1 收尾要关**。

**四条路的实测朝向（2026-11-05，同一台只有 OpenSSH 的目标 = Ubuntu-1，目的地 10.99.0.10:8000）**：
`chisel … R:<port>:socks` = 200；`ssh -N -R <port>`（不带目的地）= 200；`ssh -N -R <port>:<host>:<port>` = 读到内网主机的 SSH banner；
**`ssh -N -D <port>` 与 `ssh -N -L` = 超时**。原因是 `-D`/`-L` 的目的地由**远端**发起，这里远端就是控制端，
而控制端被段规则拦住——监听开在哪一侧不代表出口在哪一侧，此前 §6.5 记的"ssh -D/-L = 200"是把
"端口在听"当成了"流量打得通"，正是这条错记让反方向的命令一直留在选型里。`-R` 的两个前提：
控制端 sshd `GatewayPorts=clientspecified|yes`（否则拒绝在非回环上监听，现象是 ssh 活着但没监听），
以及目标到控制端免密（命令带 `BatchMode`，不同用户名会秒挂——故新增 `JINGWEI_PIVOT_SSH_USER`）。

**A1 已跑通的部分（用产品自己的 API，不是手工隧道）**：凭据入台账 → SSH 会话以 `pivot` 身份建立 →
隧道 create→probe→plan→deploy→verify 拿到 **verified**（`plan` 产出 `chisel client '…:8788'
R:0.0.0.0:11080:socks`，`listen_side=pivot`，复核 `pivot:tcp:11080` 与控制端实测一致）→
`POST /api/scans`（targets `10.99.0.0/28` + `10.99.0.20`，ports 9 个，proxy `socks5://…:11080`）**跑完**：
15 IP / 4 开放端口 / 2 服务，资产回流 6 行（`10.99.0.10` redis:6379+http-alt:8000、`10.99.0.20` ssh:22+http:80），
findings 1 条（Redis 暴露 high），自动派生的 sqlmap/dalfox 专项任务也带着同一代理打到 `http://10.99.0.10:8000/login`
并留下原始报文（200）；负向对照：容器直连 10.99.0.10:8000 超时，说明这些资产只能经隧道取得。
teardown 到 `stopped`、控制端监听消失、目标侧 pid/log 已清、`/api/managed-resources` 三条 tunnel 全 released、
`/api/managed-resources/audit` 的 `unmanaged` 为空。**A1 的 chisel 这条路到此闭环。**

过程中抓到并修掉的缺陷（都已进 CHANGELOG Unreleased）：
1. **生成 chisel / `ssh -L` 命令时丢了 `listen_host`**——chisel 因此只绑控制端回环，
   跑在另一个 netns 里的平台进程拨不到，verify 判失败（已修，`c817a94`）。
2. **ssh 变体方向反了**：选型生成 `ssh -D` / `ssh -L`，它们的目的地由控制端发起，
   对"穿透到只有目标可达的段"毫无作用；改成 `ssh -R` 后同一目标同一目的地才第一次真打通。
   教训记入开发手册：**"监听在听"不等于"流量打得通"**，隧道这类东西必须端到端取一次数据。
3. ssh 隧道缺少控制端用户名（`JINGWEI_PIVOT_SSH_USER`），跨用户名场景在 `BatchMode` 下静默秒挂。
