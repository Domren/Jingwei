  11-11 11:19/11:21 又补两种形态：中转端回 **504 网关超时** 与 **502 `Upstream request failed`**，
  同样落 `other`；12:23 补 **429 限流**（`Upstream rate limit exceeded`）；13:24 补 **404 `model_not_found`**
  （`Model "DeepSeek-V4.1-Flash-1017" is not supported by any configured account in this group`）——
  这四种加上「本地 DNS 到回环」一共**五种处置完全不同的故障，在留痕里现在都是同一个 `other`**：
  DNS 该修解析、限流该退避、5xx 该重试或换端点、model_not_found 该改模型名，谁也不该照同一个方子办；
  ② `server/llm_health.go` 的告警判据是 `failure_rate>30% 且 total>=10`：任务只被一两个边沿唤醒、
  每轮即废时轮数凑不满 10，**该响的不响**（任务 #5 实测 `failure_rate=1 / alarm=false`）；
  要改成与轮数无关的判据（连续 K 轮全废 / 首轮即不可达就响）；③ `server/engine.go:947` 构造 `RoundMeta` 没带
  `Model`/`ProfileName`，`llm_rounds` 两列落空，事后定位不到端点；④ 重试次数没接出来（日志两次重试、
  表里 `attempts=0`）；⑤ **失败轮不 commit 触发带来的空转**（11-11 10:53 重启任务 #4 实测）：失败轮故意把触发
  留在 pending（R21 ④「不丢触发」），唤醒条件于是立刻再次成立——planner 每 20–30 秒整轮、每轮 2 发各带 2 次重试，
  全打在同一个不可达端点上，`llm_rounds` 每分钟涨两行、日志一分钟 6 行失败。**「不丢触发」必须配「失败后退避」**，
  否则这条设计在端点不可用时正好变成对端点的持续轰击，还把 ② 的告警拖到十几分钟之后才响。
  ⑥ **成功轮的 token 没记账**：11:05:27 那条 `status=ok` 的规划轮 `input_tokens`/`output_tokens` 都是 0
  （`llm_usage` 侧有累计，但轮级看不出这一轮烧了多少），R15 要的「按轮回答成本」还差这一格；
  ⑦ **进行中的轮不落表**：`llm_rounds` 只在轮结束时写行，11:03:58 起的那一轮飞到 11:05:27 才出现，
  中间 89 秒「有没有轮在跑、跑到哪」仍只能翻日志——L1 的 `first_event_at` 明明有值，却是结束时回填的。
  ⑧ **同一轮重复落行，废轮率被虚高**（11:16 实机抓到）：`4-plan-6` 一条轮出两行
  （`error/other` + `stalled/stalled`）。成因清楚：`llmrec/supervisor.go:150` 的 `watchFirstEvent` 在 T1 到点时
  先 `record(context.Canceled, stalled)` 落一行，紧接着引擎那侧 `supRound.End(err)` 又用同一个 round
  落一行，两边没有「本轮已记账」的守卫，`round_id` 上也只有普通索引没有唯一约束。后果有两个：
  轮数/废轮数/`failure_rate` 全部按行算，遇到 stalled 就双计；而我们自己 cancel 出来的
  `context canceled` 在第二次记账时被分类器判成 `other`，同一次故障在表里同时是 `stalled` 和 `other`。
  修法是加一个 `recorded` 守卫（或对 `round_id` 建唯一约束改成 upsert），并把「自己 cancel 的
  `context.Canceled`」在分类里归到触发它的那一类，而不是 `other`。
  ⑨ **分类只看整轮的最终错误，内层每一发的真实形态被吞掉**（12:23–12:24 实测）：中转端已经回
  **429 `Upstream rate limit exceeded`**，但 `llm_rounds.by_class` 里始终没有 `rate_limited`——
  因为分类器拿的是 `planner.Plan()` 最终返回的那个错误，内层重试遇到的 429/502/504 在重试成功后
  就不留下了，最后落进来的往往是 `context canceled` 这类二次形态。后果：① 的「按类处置」（限流该退避、
  不可达该换端点、上游 5xx 该重试）现在**建立在丢失了原因的信息上**。修法与 ⑧ 同源：把每一发的
  错误形态随轮汇总落一行（`per_attempt_classes` 之类），分类按「最后一次有意义的错误」判，
  而不是按最外层的取消判。
  ⑩ **`T1=45s` 对这个中转端是压线值**（16:02:25 那轮实测）：它 16:03:08 才来首帧——**43 秒**，
  差 2 秒就被 L1 判成 `stalled` 砍掉，而那轮本身跑了 11 分 47 秒并成功提交（是 11:51 之后近 4 小时里
  第一个 `ok` 轮）。也就是说阈值再紧一点、或对端稍慢一点，健康的长轮会被我们自己的止损误杀。
  建议 T1 做成可配且默认放宽（60–90s），或按「同端点近期首帧延迟」自适应，而不是固定 45s。
  另外 `DefaultStalledRounds` 只是常量+setter，L3 零进展判据没接进循环，「无声停摆」这一半仍未闭；
  `JINGWEI_LLM_FIRST_EVENT_TIMEOUT` 的纯数字写法两边解析口径不一致。
  这几处合起来不到一天，建议排在 R17 之前——它直接决定下次端点再废时能不能一眼看出废在哪、并且不再空转。
- **不做**：为了让长任务「看起来在收敛」而放松 goal 判定口径。

### 5.4 设计与实现口径：LLM 活性监督与中断恢复（R21，2026-11-11 已实现并重建到 `1.6.2-dev`；L1/L2 实机生效，L3 未做。**2026-11-12 补记：十条补丁落地后 L1/L2/L3 代码侧均已闭环，见 §5.2.2，实机复跑未跑**）

前提共识：**「在工作」的定义是有进展，不是进程活着**。今天这个任务跑了 16 小时、71 轮、
96.4M 输入 token，`goal met` 仍是 0——只靠「进程在」这套判据完全看不出异常。

**① 三层判据**

| 层 | 信号 | 判定阈值（建议默认，实现时做成可配） |
| :-- | :-- | :-- |
| L1 传输 | 每次 LLM 调用的**首个流事件**时刻 | 超 `T1=45s` 无事件判 `stalled`，主动 cancel 这一发 |
| L2 轮次 | 每轮 `status / error_class / attempts / trigger_src` | 轮要么产出、要么显式失败计数，禁止无声结束 |
| L3 任务 | goal met 增量、intent 状态迁移、新资产/新漏洞、token 消耗 | 连续 `N=5` 轮零进展 → `stalled_task`，停下来问人 |

现有 `llmCallTimeout` 默认 15 分钟是给 thinking 模型留的宽口子，**不能用它判卡住**：
一轮卡满 15 分钟期间 `inflight` 一直被占着。L1 就是新增的那把刀。

**② 留痕不依赖正文录制开关**（R15 的正解）：新增 `llm_round(task_id, round_no, trigger_src,
status, error_class, attempts, profile_id, tokens_in, tokens_out, started_at, last_event_at)`，
幂等迁移；`llm_profile_health` **无论池是否启用都记失败**——启用只决定「要不要切换」，
不决定「要不要记账」。

**③ 五类错误与处置**（分类才有不同动作，否则只能统一重试）

| class | 例子 | 处置 |
| :-- | :-- | :-- |
| `transport_reset` | `stream ID 633; INTERNAL_ERROR`、connection reset | 同 profile 重试 1 次 → 退避 5/15/45s → 再失败切链 |
| `stalled` | 建连成功但 `T1` 内无事件 | cancel 后按 `transport_reset` 处理，并计入该端点劣化率 |
| `rate_limited` | 429 / 队列满 | 按 `Retry-After` 退避，**不计入熔断**（限流不是宕机） |
| `account_invalid` | 401 / 402 / 403（今天两条 profile 就是这样） | **不重试**：立刻判该配置不可用、切链或停任务，提示「欠费/未订阅」 |
| `empty_response` | 完成但无 content block | 走已有空响应重试语义 |

**④ 中断后的继续机制——三条不丢**

1. **触发不丢**：`drainTriggers()` 改成失败回灌或 peek-commit，杜绝「worker 完成了但 planner
   从没看到」而永久停滞；
2. **钱不重复烧**：重试轮不得重复创建同源意图（复用 `CompareAndSetIntentState` 的 CAS），
   且本轮已产出的意图要先落库再算成功；
3. **状态不乱**：三条既有不变量必须保持——终态任务不重规划、pause 可取消、goalless 不跑 planner。
   链耗尽时落新状态 **`llm_unavailable`**（不再用 `created`/`running` 二义表达），并**停掉 heartbeat 空转**。

**⑤ 预算与收敛闸门**（与 R19 一并解决）：任务级 `max_rounds`、`max_input_tokens`、wall clock
（`timeout_seconds` 已存在，等 R12 重建后生效）+ 进展停滞自动判定；到限就收尾并输出
「哪些 goal 没完成、还差什么」，不许无限续命。

**⑥ 看得见**：任务详情显示「当前轮：流式中 / 重试第 k 次（原因）/ 已切链 / 等 429 退避」；
新增 `GET /api/tasks/{id}/llm-health`，形态抄 `guard_denials` 的按成因分布；废轮率超阈值
（建议 30%）直接告警「该中转端不可用」——今天实测 **45%**。

**⑦ 判据反向验证**（I4 老规矩）：夹具必须人造 `stalled` / `transport_reset` / `account_invalid`
三种故障，断言「被检出 → 按类处置 → 留痕进 `llm_rounds` → 不重复烧钱」；**人造坏轮必须能让流水线红**，
否则这层门是摆设。

**⑧ 落地位置与状态**：`server/engine.go`（plannerLoop 与 triggers）、`llmpool/`（分类与记账）、
`llmrec/`（事件时间戳）、`db/`（新表迁移）、`server/llmpool.go` 与前端任务详情。
改的是执行循环：已落地并随 `jingwei:1.6.2-dev` 上过实例（`llmrec/supervisor.go`、`db/llm_rounds.go`、
engine 的 peek-commit、`server/llm_health.go`）。**L1/L2 实机生效**（任务 #5 第一轮在 `llm_rounds` 落行、
`llm-health` 可查，见 §4.3）；**L3 未实现**（`DefaultStalledRounds` 只是常量+setter，没有判据读它），
分类与告警判据另有四条缺口（§5.2 批 G）——按设计的三层判据衡量，本条只能算「两层落地、一层缺口」，

- **2026-11-14 下午修复复验（批 B 收口，三缺口全部修复并实机复验通过）**：

  - **W1（已修）**：新增 `intranetValidUTF8Text`——按「无效字节占非 ASCII 比例」分流（>50% 整串 GBK 解码，否则逐无效字节换 U+FFFD）。关键发现：GBK 字节流里存在恰好合法的 UTF-8 组合（如「功」尾字节+「完」首字节拼出 U+00E9），**逐段切分会切错，必须整串转**。修复位置 `server/intranet_scripts.go` 保存处；复验 `win-admins` 200，中文（「管理员对计算机/域有不受限制的完全访问权」）完整还原。
