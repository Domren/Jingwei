# docs 索引

这里放的是**随代码走的工作手册**：换机器、换人、隔三个月回来接手，靠这几份文档把上下文接上。
与 README.md 的分工是：README 讲「这个产品能做什么、怎么装」，这里讲「这个项目是怎么做到今天的、
下一步该做什么、哪些坑已经踩过」。

## 入库的四份

| 文档 | 什么时候读 | 内容 |
| :-- | :-- | :-- |
| [开发手册.md](开发手册.md) | 动手写代码之前 | 工程约定、测试规范（隔离库与 DSN 口径）、构建与发版流程、已踩过的坑 |
| [进度手册.md](进度手册.md) | 想知道现在做到哪了 | 当前实例状态、版本进度、正在做的事与下一步优先级 |
| [开发规划表-1.5.0-1.6.0.md](开发规划表-1.5.0-1.6.0.md) | 决定做什么、怎么验收 | 逐条工作项：类型、涉及位置、验收标准、规模、依赖 |
| [交接文档.md](交接文档.md) | 接手一台陌生机器 | 环境事实（WSL/磁盘/靶机网络）、恢复步骤、历史上做过的操作 |

另有两份专题说明：

- [漏洞流量证据.md](漏洞流量证据.md)：证据链设计（原始报文身份、多步 POC 绑定）。
- [弱口令字典维护口径.md](弱口令字典维护口径.md)：内置字典分档（core / vendor）、版本号规则、
  加条目的门槛与复核节奏。改 `scanner/credscan_dict.go` 之前先看它。

## 刻意不入库的东西

| 内容 | 为什么不入 |
| :-- | :-- |
| `公众号-*.md`、`公众号封面-*.png` | 对外宣传稿与大二进制（单张封面 2.3 MB），不是工程资料；仓库不带二进制，不配 git-lfs |
| `online-lab-*/` | 在线靶场的原始证据：抓包、截图、提交流水，里面是在**别人运营的平台上**的会话与 flag |
| `进度与下一步.md` | 逐轮历史记录，含在线平台的账号口令与一份私有文档链接；历史结论已经整理进进度手册 |

要改这个边界时，改 `.gitignore` 里 `# docs` 那一段，并同步本表。

## 入库前过的脱敏清单（2026-11-05）

四份手册逐条过下面几项，结论写在后面：

1. **真实公网 IP / 域名 / 在线赛题 URL** —— 全文没有 IPv4 字面量，网络拓扑一律写
   `<内网IP>`、RFC1918 段（`10.99.0.0/24`、`172.17.0.0/16`）或占位主机名。出现的域名只有
   `ghcr.io`（本项目镜像仓库）、`goproxy.cn`、`registry.npmmirror.com` 这类公共基础设施，
   以及一个公开上游仓库的 GitHub 链接。**通过**
2. **任何口令、token、私钥、sidecar 管理员口令** —— 只有读取方式（`docker exec … printenv`、
   `<PW>`、`${PW}`）和「不落盘、不回显」的纪律，没有值。**通过**
3. **内部阶段代号 P0/P1** —— 已改成能力名。全文剩下的 `P0/P1/P2` 只出现在两处：
   开发手册里「不要写内部代号」这条规则本身，和规划表里 A5 的清单条目。**通过**
4. **靶机拓扑细节** —— 保留，但一律用文档网段与发行版名，不指向任何可被外部访问的地址。**通过**
5. **大二进制** —— 不提交（封面 PNG 已排除），仓库不依赖 git-lfs。**通过**

## 维护约定

- 文档里写事实与原因，不写只有当时才懂的代号；引用代码时给路径，行号会漂。
- 新增一份要长期维护的手册时，先加进上面的表，再决定 `.gitignore` 怎么配。
- 每次大版本发版前，把上面 5 条清单重跑一遍——文档会随时间积累出当时看起来无害、
  后来变成泄露面的内容。
