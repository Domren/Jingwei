## 0. 这是什么 · 底线 · 署名口径

一个**自动化红队渗透平台**，Go 后端 + Next.js 前端，**只通过 Docker 镜像分发**（GHCR）。

**一句话定位**：**不配 LLM 也能完成端口探测、指纹识别、POC 命中与注入类专项验证；配上 LLM 才做
全链自动规划与深挖。** 这句话不是营销词——它是产品底线，代码里到处体现（`server/scans.go` 的无 LLM
流水线、`scanner/` 的独立内核、LLM 只是通过工具接口调用同一批能力）。**任何改动如果把「必须有 LLM
才能跑」重新引入，就是走回头路。**

**上游署名口径**：上游是 **Autumn-27/ARTEX**（现由 RuoJi6/ARTEX 维护），AGPL-3.0，保留原始提交历史。
署名以 `NOTICE` 与 `README.md` 顶部为准，**不要改**：只提 Autumn-27，保留一个可点验的上游链接。

**功能对外名**：弱口令检测（内部曾叫 credscan / 爆破，对外一律这个名）。

**四条不能改的约束**：

1. **发布物不得带敏感数据**：口令、token、私钥、真实公网 IP、测试数据都不进仓库 / 文档 / 截图 / 镜像；
2. **java-chains（闭源）绝不进 Jingwei 仓库与发布镜像**，需要时按 `deploy/JAVA_CHAINS.md` 自起 sidecar；
3. **回调 / 反连端口无认证**，默认只绑 `127.0.0.1`（`JAVA_CHAINS_CALLBACK_BIND`），不得公网暴露；
4. **公开文件（CHANGELOG / README / DEPLOY / release-notes）不引用内部台账、不使用内部代号**——
   内部编号与阶段代号只出现在 `docs/` 这两本手册里。

## 2. 三种跑法

```bash
# A. 开发模式：后端 :8787 + 录制代理 :8788 + 前端热更新（/api 反代到后端）
./dev.sh

# B. 单二进制（前端内嵌，最接近生产形态）
cd web && npm run build:static && cd ..            # 产出 web/out
rm -rf server/webui/dist && cp -r web/out server/webui/dist
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -tags embedui -trimpath \
  -ldflags "-s -w -X main.version=1.6.1" -o dist/amd64/jingwei ./cmd/jingwei
./dist/amd64/jingwei -addr :8787 -proxy 127.0.0.1:8788

# C. Docker（生产形态）
docker compose up -d          # 根目录 compose：postgres + jingwei（+ 可选 java-chains）
```

版本号只在 `-ldflags "-X main.version=..."` 里注入；不带就是 `dev`，界面右上角会显示「版本 · dev」——
**截图和验收前务必带上真实版本号**（这个坑踩过：热换的二进制没带版本，截图上写着 dev）。

## 3. 构建

### 3.1 `build.sh`

`./build.sh` 单目标构建（默认 linux/amd64，复用已导出的前端）；`./build.sh --release` 多目标打包。
常用环境变量（脚本头部注释是权威版本）：

```
JINGWEI_TARGET_OS / JINGWEI_TARGET_ARCH / JINGWEI_TARGETS
JINGWEI_BUILD_VERSION        写进二进制与包名
JINGWEI_SKIP_FRONTEND=1      复用 server/webui/dist（CI 用 artifact 时靠它）
JINGWEI_SKIP_NPM_CI=1        不重装前端依赖
JINGWEI_PACKAGE=1 / JINGWEI_COMPRESS=off|auto|required
```

### 3.2 镜像

```bash
docker build --network=host --build-arg TARGETARCH=amd64 -t jingwei:1.6.1 .
```

三条必须知道的约定：

1. **镜像里不编译代码**。运行镜像只装工具链 + `COPY dist/${TARGETARCH}/jingwei`。所以构建镜像前，
   前端 `web/out` 和对应架构的二进制必须先备好（§2 的 B）。
2. **不要加 `# syntax=docker/dockerfile:1`**。加了会让 buildkit 去 Docker Hub 拉外部前端，而本机 dockerd
   配了指向 `127.0.0.1:7890` 的代理且无监听，构建直接失败。Dockerfile 顶部注释写了这件事，别删。
3. 基础层（apt / node / nuclei / sqlmap / webcrack / dalfox / playwright）很重，**清过 build cache 之后
   整体会跑 20–40 分钟**（本机实测）。别在前台等，用后台任务跑。

`--build-arg` 可选：`PIP_INDEX_URL`（默认中科大源）、`WEBCRACK_OCR=true`（装 ddddocr，约 200MB）、
`PLAYWRIGHT_DOWNLOAD_HOST`（默认 npmmirror）、`NPM_REGISTRY`（本机装 `@playwright/*` 时指国内源，
CI 留空即可）、`PLAYWRIGHT_MCP_VERSION` / `PLAYWRIGHT_CLI_VERSION` / `PLAYWRIGHT_VERSION`
（2026-11-05 起钉死版本，**别改回 `@latest`**：那样同一提交重建两次会拿到两套浏览器工具，
镜像与提交对不上、上游接口一变就只在某次重建后炸）。

## 4. 测试规范（这一节是本项目最独特的部分）

### 4.1 跑起来

```bash
# DSN 从测试库现取，口令不落盘、不回显
export JINGWEI_PG_DSN="postgres://jingwei:<PW>@127.0.0.1:55433/jingwei_gotest?sslmode=disable"

gofmt -l . | grep -v node_modules
go vet ./...
go test ./... -count=1              # 并行
go test ./... -count=1 -p 1         # 串行
```

上面这四条要一条条设环境变量手敲，容易漏。**日常直接跑 `tools/four-test.sh`**：DSN 现取不回显、
四种口径各写一份日志、末尾汇总；它开头还会**把 HEAD 单独检出编译一遍**——有两次「功能只在工作树里、
没进提交」，工作树测试全绿而按提交检出编不出来，只有这一步拦得住。还有一件事它替你设好了：
`TMPDIR` 指向磁盘。默认的 `/run/user/0` 是几百兆 tmpfs，并行时 `go test` 往里面拷测试二进制会写爆，
报出来是 `fork/exec .../*.test: no such file or directory` 和一批「服务没起来」的假故障——
看着像代码问题，其实是磁盘问题。

**DSN 变量只有一个：`JINGWEI_PG_DSN`**。代码里没有任何地方读别的名字（`JINGWEI_TEST_PG_DSN` 之类是编出来的），
没设它时 `server/testmain_test.go` 走 `db.DSN()` 失败分支直接 `m.Run()`，纯函数测试照过、
要写库的测试**成批报「未找到数据库配置」**——一行错误信息就写明缺什么，别把它当成代码回归。
另外它必须指向隔离库 `jingwei_gotest`（本机 `127.0.0.1:55433` 的 `jingwei-test-pg`），
**不要指实例库**（`5432`）：`OpenTestSchema` 虽然按 schema 隔离，但 `JINGWEI_TEST_ALLOW_DB_WIPE=1`
配合错 DSN 就是拿实例库当试验田。跑前 `docker exec jingwei-test-pg printenv POSTGRES_DB` 确认一下，别凭记忆。

**DSN 两种写法都要过**：URI 形式（`postgres://...`）和 keyword/value 形式
（`host=... port=... user=... password=... dbname=... sslmode=disable`）。
原因：1.4.0 收尾时并行全量「通过」只在 URI 形式下成立，keyword 形式因为拼接方式无效而整批失败
（`#191` 之后修的）。**在 shell 里拼 DSN 时用变量（`password=${PW}`），别写占位星号**——
`password=***` 会被当成真口令，报 `SASL auth: password authentication failed`，看着像代码坏了。

**新增 Go 模块前先确认代理可达**：仓库没有 vendor 目录，`go get` 依赖 GOPROXY。
宿主 Clash 关着时 `proxy.golang.org` 不可达（`goproxy.cn` 通），本机开发要
`go env -w GOPROXY=https://goproxy.cn,direct`（只改本机 Go env，不进仓库；CI 用默认值即可）。
`go list -m -versions <module>` 能列出版本就是通了。

### 4.2 隔离机制（改动测试相关代码前先读）

- `db/test_schema.go`：`OpenTestSchema(baseDSN, schema)` 给**每个包**开独立 schema + 套件锁；
  `withSearchPath` 负责把 schema 注进 DSN——URI 形式写 `options` 查询参数（并合并已有的 `-c` 设置），
  keyword 形式追加 ` options=-csearch_path=`，**如果 keyword DSN 里已经有 `options=` 就直接拒绝**。
- `agent/testmain_test.go`、`server/testmain_test.go`：打不开隔离 schema 就**响亮中止**
  （`打不开隔离 schema，拒绝在共享表上跑` + `os.Exit(1)`）。以前是静默继续，于是测试在生产表上跑。
- 会清表的测试自己也要有闸：`server/chat_llm_resolve_test.go` 里若 `llm_profiles` 已有数据，
  除非 `JINGWEI_TEST_ALLOW_DB_WIPE=1`，否则 `t.Skipf` 拒绝清空——那是使用者的真实凭据。
- **隔离 schema 是跨轮次复用的，脏状态会连锁污染后续用例**（2026-11-13 踩到）：11-12 的失败轮在
  `jingwei_test_server` 留下 13 个 `created+queued` 任务，加上某条用例把
  `task_concurrency_enabled` 改成 true 没还原，测试环境又没有可用 LLM，于是
  `reconcileConcurrency` 把每个新建任务都停进队列，归档/深挖/备注/goal 播种 5 条用例全红——
  看起来像状态机缺陷，实际是测试卫生问题。现在 `server/testmain_test.go` 每轮开跑前会
  把残留非终态任务置暂停、释放队列占位，并把并发开关复位为关；**改测试时别把这两个复位删掉**，
  需要验并发的用例自己显式打开并在 `defer` 里还原。

**结论：新增需要数据库的测试包，必须走 `OpenTestSchema`，并在 TestMain 里对失败情形直接退出。**

### 4.3 抖动与时间边界

会随时间抖动的东西要显式钉住，不要靠重试掩盖：

- `evidence` 的快照身份包含**秒级 `captured_at`**（`RawExchange.CapturedAt`，0 表示取当前时间）。
  跨秒时同一份报文会算出不同 id，测试就会偶发失败（`#191` 里那个「got 4」）。测试必须传固定时间戳。
- 清理夹具时**别用 `array_agg` 直接扫进 `*[]string`**（unsupported Scan），而且错误只 log 不 return
  会让清理「半失败」还不报警。改成逐行读，见 `evidence/store_test.go` 的 `purgeEvidenceFixture`。
- 疑似抖动的包用 `-count=6` 复跑确认（`go test ./evidence -count=6`）。
- **chisel 的方向语义只能实测，别信直觉**（2026-11-05 真机结论，已钉进
  `server/intranet_pivot_port_test.go` 与 `intranet_recon_test.go`）：
  `R:<port>:socks` / `R:<port>:<host>:<port>` 的**监听在控制端**（chisel server 持有该端口），
  拨号目的地由目标发起，所以这是打内网的正确形态；不带 `R:` 的 `<port>:<host>:<port>` 反过来——
  目标监听、由控制端拨目的地，打不到只有目标可达的段。「目标监听且目标拨号」（等价 socat）
  chisel 表达不了，只能拒绝。控制端必须 `chisel server --reverse`，否则 `R:` 请求被服务端拒。
  另外 `--fingerprint` 没有 `auto` 这个值：客户端会拿整串当 SHA-256 指纹校验，握手失败后无限重试，
  表现为「进程在、日志一直 Connected 之前报错」，很容易被误判成网络问题。
- **`ssh -D` / `ssh -L` 不是穿透方向，`ssh -R` 才是**（2026-11-05 真机结论）：这两个选项的监听确实开在
  执行 ssh 的那一侧，但**目的地一律由远端发起**——把命令下发到目标机上跑，远端就是控制端，于是出口在
  控制端，穿不到只有目标可达的段。`ssh -N -R <监听地址>:<端口>`（不带目的地）才是 OpenSSH 版的反向 SOCKS：
  控制端 sshd 监听、连接转回目标的 ssh 客户端拨目的地；带目的地时 `-R <地址>:<端口>:<主机>:<端口>`
  等价 chisel 的 `R:`。前提是控制端 sshd `GatewayPorts=clientspecified|yes`，否则它拒绝在非回环地址上监听，
  而 ssh 进程自己不退——只有 verify 会暴露它。
- **验收隧道要"经它取一次目标侧独有的数据"，`verify` 只证明有人在听**：上面那条错记（"ssh -D/-L = 200"）
  就是这么来的——端口通、进程活着、台账 verified，但一次真实请求都没发过。判方向对不对最省事的办法是
  找一个**只有目标能访问**的目的地（靶场的隔离段就行），拿它当唯一验收口径。
- **`.env` 里的 `JINGWEI_IMAGE` 写成一个还没构建的标签，会造出「标签与内容不符」的假镜像**：根
  `docker-compose.yml` 带 `build:`，`docker compose up -d` 找不到该标签时就地用当前工作树构建，
  用的还是 `dist/amd64/jingwei` 里上一次留下的二进制——这次标签写 `1.4.2`、`/api/health` 却报 `1.4.1`
  （2026-11-04 实际发生，且因为我并发跑了一条超时后转后台的旧命令，回退 `.env` 之后容器仍留在假镜像上）。
  做法：切版本前先 `docker images jingwei` 确认目标标签存在；切完用 `/api/health` 的版本串核对；
  后台还在跑命令时不要同时改 `.env` 与 compose。
- **别用 `cmd 2>&1 | tail -N` 判断成败**：管道返回的是最后一个命令的退出码，`docker build`/`go test`
  失败也会被报成「exit 0」（2026-11-04 一天内两次：把失败的构建当成成功去切 `.env`、把失败的测试当成通过）。
  要么 `set -o pipefail`，要么先落日志文件再取，退出码单独判断。

## 5. 前端约定

- 静态导出：`NEXT_EXPORT=1 next build`（脚本 `npm run build:static`），产物 `web/out`，构建时拷进
  `server/webui/dist` 并用 `-tags embedui` 内嵌。
- 页面在 `web/src/app/(main)/function/**`；「深度利用」二级页在 `function/deep/**`。
- **终端组件只有一份**：`function/deep/_components/shell-terminal.tsx`。WebShell 工作台和内网会话共用它，
  不要为第二种承载另写终端（`#187` 就是把它合并的）。
- 演示数据：`NEXT_PUBLIC_MOCK=1` 时 `src/lib/api.ts` 短路进 `src/lib/mock/handler.ts`，无需后端。
  注意 mock 覆盖不全（例如 `/api/intranet/*`、webshell 系列没有）。发现页曾因 mock 缺少
  `/exploration/findings/systems` 与 `/ids` 端点而崩溃，已于 1.4.1 补齐（CHANGELOG 1.4.1）；
  其余未覆盖端点仍可能返回空数据，改动发现页时保持对空数组的防御。
- **hydration**：静态导出下服务端 HTML 与首屏客户端渲染必须一致。凡是依赖 `Date.now()`、`localStorage`、
  窗口尺寸的值，都要**等 mount 之后再 setState**（首帧渲染 null / 占位）。请求重发页的时钟就是这么做的。
- 浏览器偏好统一用 `jingwei.` 前缀的 localStorage 键，例如 `jingwei.repeater.clock`（存 `{offset}`，
  读写都要夹在合法范围内）。
- 代码风格用 biome：`npm run check` / `npm run check:fix`。

## 6. 加一条新能力要动哪几处

本项目的能力基本都是「表 + 存储层 + API + agent 工具 + 前端 + 台账」六件套，少一环就会出现
「CLI 能用、页面看不到」或「页面能点、agent 调不到」。

1. **数据模型与迁移**：`db/`（建表 + 启动迁移；迁移要幂等，容器重建会重跑）；
2. **存储层**：`db/*.go`，查询助手注意「空值语义」——例如 `QueryByType("")` 现在表示**不加类型过滤**，
   以前会被兜底成 `root_domain`，直接把内网拓扑页打死（1.4.0 修的那个）；
3. **HTTP API**：`server/`，路由集中在 `server/server.go` / `server/intranet.go` 的 `mux.HandleFunc`；
   错误信息要**可读且区分成因**（超时 / 拒绝连接 / 目标没答 不能压成同一句）；
4. **agent 工具**：让 LLM 也能用同一能力（`agent/`），并过 `guard/` 的目标范围与出站限制；
5. **前端页面**：`web/src/lib/api.ts` 加方法 + 对应 `page.tsx`；
6. **台账与资源回收**：会占用端口/文件/进程的能力必须登记进 `managed_resources`（带 TTL，到期自动回收），
   落地物进 `intranet_artifacts`（带撤销命令与验证命令，撤不动就不许登记）。

另外两条硬规矩：

- **证据**：任何「漏洞结论」都必须带原始报文（`evidence/`）。多步 POC 存整条链；非 HTTP 协议按协议出
  十六进制字节；报告逐步绑定流量快照。**「见截图」式占位会被证据质量校验拦下。**
- **口令**：写进去、不读出来。凭据台账接口只回 `has_password`，明文永不下发浏览器。

## 7. 密钥与密封（改这块前务必读）

- 签名根密钥存在 `platform_secret`（单行表）。启动顺序：**库优先 → 旧 `/app/jwt.key` 迁移入库后删除 →
  都没有才生成并写库**。它同时是三样东西的根：会话 JWT 的 HS256 签名、webshell/内存马/半持久化的密钥密封、
  内网口令与模型 API 密钥的派生加密。
- 因此**容器重建不再让已投放的壳变成砖**，也不再让所有人重新登录。这是 1.4.0 最重要的一条不变量。
- 首次启动会把 `intranet_credentials.password`、`llm_profiles.api_key` 就地改为密封存储并写
  `secret_seal_v1` 标记，重复启动不再处理。
- 如果数据库被还原到换密钥之前，密封值不可解：启动日志要**按类别**打印解不开条数与补救动作
  （重投载荷 / 重新注入 / 重新登记凭据 / 重填模型密钥），不要只报一句「解密失败」。

## 9. 发布流程与发版 checklist

### 9.1 顺序（谁做、按什么次序）

1. 代码与文档改完 → 全量验证四种口径都过（`tools/four-test.sh`，含 HEAD 检出编译）；
2. 更新 `CHANGELOG.md`、`README.md`（**顶部能力段 + 版本历史小节两处都要**）、
   `.github/release-notes/vX.Y.Z.md`、`DEPLOY.md` 与 compose 的默认 tag、`web/package.json`；
3. 敏感信息扫描 → 提交（heredoc）→ **先定发版提交再跑四组合门**；
4. `git push origin main` → **新建附注标签** `git tag -a vX.Y.Z` → `git push origin vX.Y.Z`；
5. 等 CI（`prepare` / `frontend` / `ui-visual` / `binaries`×2 / `docker`×2 / `docker-publish` / `release`）全绿；
6. 核对 Release 正文与三附件、GHCR 三个 tag 同 digest 且双架构（§1.2 的匿名 manifest 命令）；
7. 本地 `docker compose pull && docker compose up -d`，再做一次升级后验收（登录、两套壳存活检测、日志无 panic）。

### 9.2 版本号与标签策略（**1.4.1 起的硬规则**）

- **已发布的标签不移动**。同一版本号对应两个 digest 会让用户侧的「我装的是哪个」无法回答；
  1.4.0 那种「移动标签重发」不再做，当年的五次重发只是历史（见进度手册 §2）。
- **含功能或修复的代码改动走新版本号**：安全修复走 patch 小版本，功能版本才动 minor；
  纯文档/截图改动可以直接改 `[Unreleased]` 随下一版走，不单独发版。
- **新标签一律附注标签**（`git tag -a`）。打之前先 `git cat-file -t v<上一版>` 核对形态；
  轻量标签推错了要删了重打，同 SHA 会白跑一遍 CI（1.6.0 踩过：两个 run 产物一致，但台账要写清）。
- 版本号只在 `-ldflags "-X main.version=..."` 里注入，CI 从 tag 取（§2）。
- 每次发版**需要负责人逐次授权**：推 main 可以按计划走，打 tag / 发 Release 每次单独确认。

### 9.3 发版 checklist

- [ ] 全量验证四种口径都过：并行、串行、URI DSN、keyword DSN（`tools/four-test.sh` 一把跑完，含 HEAD 检出编译）

| 现象 | 根因 | 现在怎么做 |

| 提交信息里的引号把命令打炸 | `git commit -m "..."` 拼接 | 一律 heredoc `-F -` |

| 镜像重建了、行为还是旧的 | Dockerfile 是「放入预编译二进制」型，二进制没编进 `dist/amd64/jingwei`（比如编到了 /tmp），build 缓存把旧层原样打包 | `strings <二进制> \| grep -c <新符号>` 对比容器内外；先重建二进制再 docker build（2026-11-13，PerCallProvider 符号定位） |

## 11. 代码风格

- **注释只写 WHY**，不写 WHAT。多段落注释一律不要，能一句话说清就一句话。
  典型该写注释的地方：幂等约束、秒级时间参与哈希、为什么不能压平错误、为什么要留 `# syntax` 那行注释。
- 用户可见的错误信息用**中文且可读**，说清成因与下一步；不要 `error: xxx failed`。
- 文档里**不要写「P0/P1/P2」这类内部代号**——外部读者不知道那是第几阶段。写清楚是什么事。
  同样地，**公开文件（CHANGELOG / README / DEPLOY / release-notes）不引用内部台账**（进度手册章节号、
  内部任务编号、内部批号都不行）；内部代号与编号只留在 `docs/` 这两本手册里。
- 不造提前抽象：三处相似好过一个用不上的接口。不做向后兼容的壳（改名留 `_var`、re-export、
  `// removed` 注释都算）。确定没人用了就删干净。
- 不加不会触发的错误处理与兜底；只在系统边界（用户输入、外部 API）校验。

### 12.1 统计口径（`tools/stats.sh`，R11）

进度手册 §1 的「代码与测试」一行不再手数，一律由脚本生成：

```sh
sh tools/stats.sh                 # Markdown 表格，直接贴进 §1
sh tools/stats.sh --json          # 机器可读
sh tools/stats.sh --check docs/进度手册.md   # 与手册逐项比对，有差异退出 1
sh tools/stats.sh --dsn "postgres://…"       # 顺带取库里的表数与 POC 条数
```

口径写在脚本头部注释里（跳过哪些目录、物理行怎么算、路由是「注册条数」还是
「唯一路径」）。**改口径必须改脚本，不能只改文档**——否则下一个人算出来的数
和手册对不上，又会退回手数。

库内两项（表数、POC 条数）只能连库实测，脚本静态数不出来就不写，不猜。
本地实例的取法：

```sh
P=$(docker inspect jingwei-postgres-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | grep ^POSTGRES_PASSWORD= | cut -d= -f2)
sh tools/stats.sh --dsn "postgres://jingwei:${P}@127.0.0.1:55432/jingwei?sslmode=disable"
```

## 14. WSL 基建与靶场重建

### 14.1 磁盘：vhdx 只增不减，收缩要按四条做

数据盘位置（2026-11-04 已搬家）：`D:\wsl-kali\Kali\ext4.vhdx`，实际占用约 43 GB，虚拟上限 1T。
以前在 Store 包目录（最长涨到 62.1 GB），搬到 D 分区后 C 盘可用从 108 GB 变 158 GB；
C 与 D 是同一块 NVMe 上的两个分区，搬家不影响 I/O 性能。**别在脚本里写死路径**，注册表现读：

```powershell
$k = Get-ChildItem 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss' |
     Where-Object { (Get-ItemProperty $_.PSPath).DistributionName -eq 'kali-linux' }
Join-Path (Get-ItemProperty $k.PSPath).BasePath 'ext4.vhdx'
```

**稀疏盘这条路在本机是死的**：`wsl --manage kali-linux --set-sparse true` 在 WSL 2.7.11 / Windows 26H2
上报 `Wsl/Service/E_INVALIDARG`（「因潜在数据损坏已禁用，强制需 `--allow-unsafe`」）。整台开发环境
（源码、docker 卷、库备份）都在这一个 vhdx 里，**不要按 `--allow-unsafe`**。

**正路：就地压缩（`Optimize-VHD -Mode Full`，盘的形态不变）**，四条关键：

1. **先起 `vmms` 与 `VDS` 两个服务**（默认 Stopped）。没起的话 `Optimize-VHD` 会在几秒内静默返回、
   reclaimed 0.00 GB——这个坑踩过两次。收缩完 `Stop-Service` 复原，别留两个常驻服务。
2. PowerShell 里 `$ErrorActionPreference='Stop'` 并打印 `$_.ErrorDetails`：Optimize-VHD 的失败是
   非终止错误，会被日志吞掉，看起来像「成功但没收缩」。Kali 的 MOTD 走 stderr，原生命令要单独降级处理。
3. **`wsl --shutdown` 之后盘不会立刻放开**：`wsl -l -v` 显示没发行版在跑，`vmwp.exe` / `wslservice`
   仍攥着 vhdx，`Optimize-VHD` 报 `另一个程序正在使用此文件 (0x80070020)`。要用
   `[IO.File]::Open($vhdx,'Open','ReadWrite','None')` 轮询确认真独占（默认最多等 120 秒），
   而不是只看 `wsl -l -v`。
4. **发起收缩的会话本身会把盘抢回去**：Agent 下一条命令就重新拉起 WSL。所以这一步必须由人
   在 Windows 侧跑，跑之前关掉所有 WSL 窗口 / Remote / 会话。

收缩前先 `sudo fstrim -v /`（根分区本来就是 `discard` 挂载）能多拿几个 GB；
兜底用 `diskpart /s compact.txt`（`select vdisk file=... / attach vdisk readonly / compact vdisk / detach vdisk / exit`）。
**收缩前必做**：`cd /root/1/jingwei-dev && docker compose stop`——`wsl --shutdown` 是硬停，会把
Jingwei、postgres 和 **Ubuntu-1/2/3 三台靶机**一起干掉，收缩完要重新 `wsl -d Ubuntu-1` 拉起；
靶机上的 webshell 与维持落地物不受影响，但服务要重启。并把不可再生的东西复制到**另一块分区**：
`/root/backups`、`docs/`、`/root/lab-ubuntu` → `/mnt/d/jingwei-pre-shrink-<date>/`
（同分区副本挡不住 vhdx 损坏；这些 dump 里含口令哈希与密封后的密钥，别往外发）。
搬家可用 `wsl --manage kali-linux --move <路径>`，失败时走 export → unregister → import；
export/import 出来的盘按实际内容重新分配，等于顺带做了一次彻底收缩。

### 14.2 拉取失败的回退口径（GHCR blob CDN 常 TLS reset）

### 14.3 靶场内网段：隔离是怎么成立的，以及重建顺序

**先理解隔离**：`readlink /proc/1/ns/net` 在 kali-linux / Ubuntu-1 / Ubuntu-2 / Ubuntu-3 上都是
**同一个 inode**（WSL 镜像网络下四个发行版共用一个网络命名空间）。所以：

- 「内网主机只能经隧道到达」**不能靠路由隔离**——Kali 天然能直接连 Ubuntu-2/3 的 2202/8090/3307。
- 唯一让段落算「内网」的机制是 **iptables 的 `owner --uid-owner` 匹配**：`JWLABINT` 链只放行
  www-data(33)/tomcat(999)，其余（含 root）对 `10.99.0.0/24` 一律 DROP。于是 root 在任何发行版都打不通，
  Web 进程能打通——这才是「边界机上的低权落地点可以进内网，分析机不行」的等价模型。
- **对隧道验证的直接后果**：隧道的 `deploy` 走 SSH 会话（`server/intranet.go` 的 `intranetExec`），
  而 SSH 进去是 root ⇒ 被自家规则拦住。要跑通「建隧道 → 经代理扫内网 → 回流 → 拆除」，
  必须把发起隧道的那个登录用户 uid 加进 `JWLABINT` 白名单（或改用 web uid 的会话执行）。
  **这不是靶场的毛病，是测试设计上的真实约束**，写用例时要显式处理。

**重建顺序（脚本是分段增量的，顺序错了就起不来）**：

```bash
# /root/lab-ubuntu 下，脚本里是 <REDIS_PASS> / <SVC_SSH_PASS> 占位符，跑之前用本机临时口令替换
./wslrun.sh Ubuntu-1 <(u1-netns.sh)        # 建拓扑
./wslrun.sh Ubuntu-1 <(u1-netns2.sh)       # 修正版拓扑：veth 语法以这份为准
./wslrun.sh Ubuntu-1 <(u1-netns-apps.sh)   # 段内应用（apt 装 redis、写 app.py、建单元）
./wslrun.sh Ubuntu-1 <(u1-netns3.sh)       # 修 FORWARD 段内互通与 redis 权限，重跑自检
systemctl restart jwlab-netns lab-intconsole lab-intredis lab-corepanel lab-coressh  # apps 写完文件后必须重启
```

踩过的三个坑：① `u1-netns.sh` 往 `/opt/internal` 写文件但 `mkdir` 只在后面的 apps 脚本里，
全新环境第一次必失败（已修）；② `ip link add <n> type netns <ns> name <n>` 这种写法在本机 iproute2
上报 `Garbage instead of arguments`，要用 `u1-netns2.sh` 里的 veth/peer 写法；③ 单元在 apps 脚本
写文件**之前**就被拉起，会留下 `active 但没监听` 的假健康，必须重启一次再自检。
netns 段 `10.99.0.0/24` **不跨重启**；靶机口令只在 `/tmp/.labredispw`、`/tmp/.labsvcpw`（600，用完删）。

**能力矩阵回归靶场**（2026-11-10 另建，与上面 netns 拓扑无关）：docker 网络 `jwlab` 10.10.0.0/24 +
`jwlab-int` 10.10.1.0/24，容器 `jw-a`/`jw-b`/`jw-c`/`jw-java`/`jw-dns` + `jw-test`（宿主 9792）+
独立库 `jingwei_lab`；测试脚本在 `/root/lab-jw16/`，台账见进度手册 §4.1。

## 附录A · 弱口令字典维护口径

代码在 `scanner/credscan_dict.go`。内置字典是「这个端口有没有低级错误」的第一轮检查，不是穷举。
这份口径定的是：**什么条目能进来、进来放哪一档、什么时候复核、改完怎么验**。

**为什么不做全量口令库**：两件事必须分开——**内置档**回答「这个服务装完没改密码」，
**导入档**（`cred_tasks.dict_profile`，操作员显式导入）回答「这个目标我怀疑有特定口令」。
把全量库塞进内置档有两个后果，都不是技术问题：跑一遍全网端口等于替操作员决定了「打多大」，
出了事没人说得清这是谁的意图；而内置档越大，预算越容易在真正该试的那几条之前耗尽。
所以默认路径永远是精简的。

**分档与版本**：内置档分两档，尝试顺序固定为 **core 全量 → vendor 全量**（顺序决定「最先试出什么」，
也决定预算耗尽时牺牲谁；不是分组并发）。分档只是给新条目一个明确位置，并让界面能说清这一版覆盖到哪
（`GET /api/credscan/protocols` 的 `builtin_dict`）。

| 档 | key | 收什么 | 判断标准 |
| :-- | :-- | :-- | :-- |
| 通用 | `core` | 空口令、`root:root`、`admin:admin` 这类与厂商无关的组合 | 任何一台设备出厂都可能长这样 |
| 厂商/设备 | `vendor` | MSSQL `sa`、Jenkins/JBoss 控制台、svnserve、RouterOS、SNMP 的 `public/private/community` | 只对特定协议有意义，但对那个协议必须靠前 |

版本号 `CredBuiltinDictVersion`，格式 `YYYY.MM`，同月内二次调整加 `.1`（例如 `2026.11.1`）。
它表示**内容版本**，不是程序版本：条目变了就跟着变，界面靠它回答「这次跑的是哪一版字典」。

**加一条的门槛（三条都要满足，缺一条就不加）**：

1. **能说出出处**：哪个产品、哪个版本、出厂或安装脚本默认就是它，注释里写清楚。
   「网上见过有人这么用」不算——那类条目的误报成本（多打一次、可能触发锁定）高于命中收益。
2. **能在 lab 里复现**：用 `tools/e2e/credscan-lab/` 起真服务，命中路径走通一次。
   起不了真服务的协议（1.6.0 已砍掉的 Oracle/WebLogic/WinRM/CobaltStrike 那一类）不加新条目。
3. **形状对**：SNMP 这类「凭据就是口令」的协议，条目必须无用户名；写进 vendor 档而不是 core。

删条目同样要理由：只有当它被证明确实不存在于任何出厂配置，或者会造成稳定的误报（例如某些服务
把空口令解释为「匿名」而不是「无口令」），才删。删的时候同步升版本号。

**复核节奏**：每季度查 vendor 档（新出的产品默认口令、已停产品条目是否还值得留）；新增协议时该协议
至少一条出厂口令进 vendor 档并补一条 lab 用例；每次发版前跑 `go test ./scanner -run TestCredBuiltinDict`
+ `-run TestCredOrder`；收到误报先查是不是「空凭据/匿名语义」导致，再决定改字典还是改适配器判据。
**字典复核不阻塞发版**：它影响命中率，不影响结论正确性。但**改了字典就要升版本号**。

**改完怎么验**：

```bash
go test ./scanner -run 'TestCredBuiltinDict|TestCredOrder' -count=1
tools/e2e/credscan-lab/docker-labs.sh up     # 或 six-pack.sh 的六条
JW_CRED_LAB=1 JW_CRED_LAB_MANIFEST=/tmp/jw-cred-lab-6/lab.json \
  go test ./scanner -run TestCredLabProtocols -count=1 -v
```

四条测试分别锁：分档合计 = 实际条目数、尝试顺序 = core→vendor、无重复条目、SNMP 条目是无用户名的
纯口令。**只加条目不跑真机，不算验证过**：进程内协议桩拿不到「服务端认不认这组口令」的结论，
1.6.0 的教训就是桩与实现按同一份错误理解写、测试一直是绿的（进度手册 §4 收尾批）。

**与协议定向排序的关系**：`OrderCredentialsForProtocol` 只做一件事——把某协议最该先试的条目提到前面
（目前只有 SNMP 的 community），**只重排、不增删**。它不能用来「临时屏蔽」某条口令：
少一条等于在报告里声称测过一组其实没测的口令。

## 附录B · 漏洞多流量证据

漏洞详情的「关联流量」支持跨页多选、用途和说明、排序及解除绑定；流量页也可多选记录一次关联到
一个已有漏洞。任务继承的漏洞证据只读，修改需进入来源任务。

**开关**：系统设置中的「Agent 自动绑定流量」默认关闭，读写走 `/api/settings` 的 `agent_traffic_binding`。
开启会增加查阅请求/响应、工具调用及提示词带来的 Token 消耗；下一轮 Agent 使用新设置。关闭时隐藏
自动绑定参数和补绑工具、不注入自动绑定指引，并拒绝已运行会话新提交的自动绑定。人工绑定、流量捕获、
已保存证据读取和导出不受影响。

**开启后的默认流程**：「发现入库 → 自动触发报告 Agent → 核对并绑定流量 → 按最新证据版本写报告」。
上报者在 `evidence` 保留验证命令、关键输出、已有真实流量 ID 及用途；报告 Agent 用 `traffic_search` /
`traffic_get` 核实后调用 `bind_finding_traffic`，再读取最新 `version` 保存报告。关闭开关时，报告 Agent
不额外获得原始流量检索/读取工具，也不自动绑定；仍能读取人工绑定的快照并生成报告。

**绑定可选**：TCP 等非 HTTP 漏洞、未采集或找不到确切记录时，省略引用仍可正常上报和撰写报告；
保留命令输出、日志等其他可验证证据，建议说明未绑定原因，不新增必填字段。兼容已有调用者：
`report_finding` 的 `traffic_refs` / `evidence_hint_id` 仍可显式即时绑定。提交的 ID 必须全部有效且正文完整；
任何一条失败都会回滚本次绑定操作，显式随上报绑定失败时整次上报回滚。重复追加同一快照不增加绑定，
也不覆盖说明。

**Agent 编号**：`report_finding` 的可选 `traffic_refs` 数组顺序即初始证据顺序，
`role` 取 `baseline`（正常对照）/ `proof`（漏洞证明）/ `verification`（补充验证）/ `supporting`
（辅助证据，默认）。域名和时间仅用于候选筛选，**不推定任务归属**；不得猜测 ID，也不应仅为补包重复探测。
返回第一行仍是 `finding recorded: <探索节点 ID>`；随后 JSON 给出 `finding_id`、`finding_node_id` 与绑定摘要。

- `get_finding_traffic(finding_id)` 用**独立漏洞记录 ID**，返回有序清单及 `version`；
  传 `binding_id`、`side=request|response`、`offset`、`length` 可分段读取，每段最多 8192 字节。
- `update_finding_report` 的 `finding_id` **继续用探索节点 ID**；新增 `evidence_version` 填实际读到的版本，
  生成期间证据变化会拒绝旧版本写入，必须重新读取并生成。旧报告未传版本时，不宣称覆盖已有流量证据。
- 绑定、说明、用途或排序变化后，已有报告提示待更新。
- 开启自动绑定后，`add_hint` / `add_task_hint` 支持在单条或批量 `hints` 的每个元素里保存 `traffic_refs`；
  Planner 代为上报可传 `evidence_hint_id`，明确选取本任务对应提示中的引用，不能引用继承提示。
  提交失败不生成部分漏洞或提前触发报告；已有漏洞漏绑可用 `bind_finding_traffic` 补绑，无需重复登记。
- `list_findings` / `list_task_findings` / `node_detail` / `get_task_node_detail` 返回明确的
  `finding_id` 与 `finding_node_id`；旧 `id` 保持探索节点语义。
- 指引在最终工具装配后统一加入：上报角色负责交接已有证据，报告 Agent 负责核对、绑定和写报告；
  平台对话缺少任务上下文时应通过结构化提示交接给任务 Agent，不直接上报。失败的 `report_finding`
  不触发报告 Agent。

**API**：基础路径 `/api/exploration/findings/{finding_id}/traffic`（用独立漏洞 ID），沿用认证；
`context_task` 校验任务可见性及继承只读。

| 方法 / 相对路径 | 请求 / 返回 |
| --- | --- |
| `GET` | 有序摘要、证据版本、报告采用版本 |
| `POST` | `{"traffic_refs":[...]}` 整批追加 |
| `PATCH /{binding_id}` | `{"version":1,"role":"proof","note":"说明"}` |

版本/排序集合冲突、归档中写入返回 `409`；继承写入 `403`；不存在或不属于漏洞的绑定 `404`；
流量/附件读取及校验失败明确返回错误。

**存储与迁移**：启动幂等迁移 PostgreSQL，新增 `traffic_evidence_snapshots`、`finding_traffic_bindings`
与 `findings.evidence_version` / `report_evidence_version`（默认 0）；**不根据历史文字猜测补绑**。
快照保存原流量 ID、采集时间、URL、方法、状态、请求/响应头、正文长度与 SHA-256；正文按哈希存放在
`<data>/evidence/blobs/<前两位>/<hash>.bin`，与可清理的 `data/traffic` 独立，多个漏洞可共享快照/正文。
快照不提供内容更新接口，校验不一致时读取和导出失败。在原流量写锁下读取完整正文（含大正文 blob 与旧目录
记录）；先持久化并校验文件，再用单个 PostgreSQL 事务写入探索节点、意图关系、漏洞、快照和绑定，提交后才
通知规划者——失败可能遗留无引用文件，但不产生部分业务记录。PostgreSQL advisory lock `7337741004`
协调证据文件与 SQL 引用；任务行锁禁止归档排队后的证据修改；恢复从正文安装到元数据提交全程保持证据锁；
删除漏洞级联移除绑定。清理器每小时运行，只回收无引用且非进行中操作的内容，至少延迟 24 小时；
普通流量清理不触及证据目录。**备份热数据时要同时备份 PostgreSQL 和 `data/evidence`。**

**导出与归档**：Markdown 含有序证据清单及版本；JSON 含元数据；CSV 增加数量与绑定 ID。`md-zip` 保留漏洞
Markdown 并提供 `evidence/<finding_id>/<binding_id>/{manifest.json,request.http,response.http,request.bin,response.bin}`，
Markdown 用相对链接引用报文。发送下载前完成附件复制、哈希校验、压缩、磁盘同步及全部 ZIP 条目的 CRC
读取校验；缺失/损坏使整个下载失败；完整附件保留二进制原字节。归档 v3 按漏洞绑定关系收集快照和正文，
不依赖原流量或域名；包校验完成后才清理热数据，共享证据继续保留；恢复先校验安装正文，再事务恢复元数据
与绑定，支持失败重试；v1/v2 继续可恢复，缺失的新字段显式补为 0。
