## 1. 这是什么

一个**自动化红队渗透平台**，Go 后端 + Next.js 前端，**只通过 Docker 镜像分发**。

一句话定位：**不配 LLM 也能完成端口探测、指纹识别、POC 命中与注入类专项验证；配上 LLM 才做全链自动规划与深挖。**
这句话不是营销词——它是产品底线，代码里到处体现（`server/scans.go` 的无 LLM 流水线、`scanner/` 的独立内核、
LLM 只是通过工具接口调用同一批能力）。任何改动如果把「必须有 LLM 才能跑」重新引入，就是走回头路。

上游是 **Autumn-27/ARTEX**（现由 RuoJi6/ARTEX 维护），AGPL-3.0，保留原始提交历史。署名口径见 `NOTICE` 与
`README.md` 顶部，**不要改**：只提 Autumn-27，保留一个可点验的上游链接。

## 5.1 WSL 磁盘收缩（在 Windows 侧做，不是在本机做）

删完文件 `df` 变小，但 vhdx **只增不减**，除非主动收缩。

**数据盘位置（2026-11-04 已搬家）**：现在是 `D:\wsl-kali\Kali\ext4.vhdx`，实际占用 43.4 GB，
虚拟上限 1T。以前它在 Store 包目录
`C:\Users\Administrator\AppData\Local\Packages\KaliLinux.54290C8133FEE_ey8k8hqnwqnmg\LocalState`，
最长涨到 62.1 GB，把系统盘挤得很紧；搬到 D 分区后 C 盘可用从 108 GB 变成 **158 GB**。
C 与 D 是同一块 NVMe（BIWIN 512G，Healthy）上的两个分区，所以搬家不影响 I/O 性能，
只是把占用从系统盘挪到数据盘。三台靶机本来就在 `D:\wsl-ubuntu\Ubuntu-{1,2,3}`。

**别在脚本里写死路径**，注册表现读：

```powershell
$k = Get-ChildItem 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss' |
     Where-Object { (Get-ItemProperty $_.PSPath).DistributionName -eq 'kali-linux' }
Join-Path (Get-ItemProperty $k.PSPath).BasePath 'ext4.vhdx'
```

（搬家后 `PackagePath` 已为空，发行版不再绑 Store 包；`wsl -d kali-linux` 与桌面/终端入口照旧可用。）

**怎么搬的家**：`wsl --shutdown` 后 `wsl --manage kali-linux --move D:\wsl-kali\Kali`；
不支持或失败时走 `wsl --export` 出 tar → `wsl --unregister` → `wsl --import`。
注意 export/import 出来的盘是**按实际内容重新分配**的，所以搬完直接就是 43.4 GB（贴着 43 GB 内容），
等于顺带做了一次彻底收缩。搬之前先 `pg_dump` 一份并复制到**另一块分区**（见本节末尾的保险清单）。

**不要用稀疏盘（这条路在本机是死的）**

```text
wsl --manage kali-linux --set-sparse true
→ 由于潜在的数据损坏，目前已禁用稀疏 VHD 支持。要强制…请运行 --set-sparse true --allow-unsafe
  错误代码: Wsl/Service/E_INVALIDARG          （WSL 2.7.11 / Windows 26H2 实测）
```

`--allow-unsafe` 就是那句「潜在数据损坏」的逃生阀，整台开发环境（源码、docker 卷、库备份）都在这一个
vhdx 里，**不要按**。想用稀疏盘的自动回收，得先把发行版搬到 WSL 允许稀疏的形态，成本远大于收益。

**正路：就地压缩（盘的形态不变）**

```powershell
# 先决条件：① Hyper-V 的 Optimize-VHD 可用  ② vmms 与 VDS 两个服务必须在跑（默认 Stopped，
#    没起的话 Optimize-VHD 会在几秒内静默返回、reclaimed 0.00 GB——这是本次踩的坑）
Get-Service vmms,VDS          # Stopped 就 Start-Service 两个
wsl --shutdown
Start-Sleep -Seconds 20
Optimize-VHD -Path $vhdx -Mode Full
# 兜底：diskpart /s compact.txt，内容 select vdisk file="<vhdx>" / attach vdisk readonly /
#       compact vdisk / detach vdisk / exit
Get-Service vmms,VDS | Stop-Service    # 收缩完复原，别留两个常驻服务
```

收缩前先在 Kali 里 `sudo fstrim -v /`（根分区本来就是 `rw,...,discard` 挂载），把空闲块标记掉，
能多拿几个 GB；**PowerShell 里务必 `$ErrorActionPreference='Stop'` 并打印 `$_.ErrorDetails`**，
否则 Optimize-VHD 的失败是非终止错误，会被日志吞掉，看起来像"成功但没收缩"。

**第三个坑：`wsl --shutdown` 之后盘不会立刻放开**。`wsl -l -v` 已经显示没有发行版在跑，
`vmwp.exe` / `wslservice` 仍攥着 vhdx，`Optimize-VHD` 立刻报
`另一个程序正在使用此文件 (0x80070020)`（2026-11-04 第二次失败实测，等了 20 秒仍被锁）。
所以收缩前要用「以 `FileShare=None` 尝试打开文件」轮询确认真的独占（脚本里 `Test-VhdUnlocked`，
默认最多等 120 秒），而不是只看 `wsl -l -v`。**发起收缩的会话本身会把盘抢回去**：Agent 下一条
命令就会重新拉起 WSL，所以这一步必须由人在 Windows 侧跑，跑之前关掉所有 WSL 窗口/Remote/会话。

**收缩前必做**：`cd /root/1/jingwei-dev && docker compose stop`（`wsl --shutdown` 是硬停，
会把 Jingwei、postgres 和 **Ubuntu-1/2/3 三台靶机一起干掉**，收缩完要重新 `wsl -d Ubuntu-1` 拉起来，
靶机上的 webshell 与维持落地物不受影响，但服务要重启）。另外把不可再生的东西复制到**另一块分区**再动手：
`/root/backups`（含搬家前的 `jingwei-pre-move-20261104-173102.dump`，`pg_restore --list` 校验过）、
`docs/`、`/root/lab-ubuntu` → `/mnt/d/jingwei-pre-shrink-20261104/`
（同分区副本挡不住 vhdx 损坏；这些 dump 里含口令哈希与密封后的密钥，别往外发）。

**现成脚本**：收缩当时写过一份 `Desktop\shrink-kali.ps1`（用完已删，别去找）。以后要收缩就照上面的步骤手敲，
关键是这四条：① 起 `vmms`+`VDS`（否则 `Optimize-VHD` 静默 0 回收）② `$ErrorActionPreference='Stop'`
并把原生命令单独降级（Kali 的 MOTD 走 stderr，会把脚本炸掉）③ `wsl --shutdown` 之后**用
`[IO.File]::Open($vhdx,'Open','ReadWrite','None')` 轮询确认独占**，别只看 `wsl -l -v`
④ 跑的人不能同时开着任何 WSL 会话——Agent 的下一条命令就会把 Kali 拉回去抢锁（本机两次失败都是这个原因）。
收缩记录：2026-11-04 三次尝试，前两次回收 0 GB（原因见 §5.1 上面两段），第三次 `62.12 GB → 50.10 GB`；
随后搬家到 D 盘时按内容重建，落到 43.4 GB。

## 5.2 靶场内网段（重建步骤与三个坑）

**先理解隔离是怎么成立的**：`readlink /proc/1/ns/net` 在 kali-linux / Ubuntu-1 / Ubuntu-2 / Ubuntu-3
上都是 **同一个 inode**（WSL 镜像网络下四个发行版共用一个网络命名空间）。所以：

- 「内网主机只能经隧道到达」**不能靠路由隔离**——Kali 天然能直接连 Ubuntu-2/3 的 2202/8090/3307。
- 唯一让段落算「内网」的机制是 **iptables 的 `owner --uid-owner` 匹配**：`JWLABINT` 链只放行
  www-data(33)/tomcat(999)，其余（含 root）对 `10.99.0.0/24` 一律 DROP。于是 root 在任何发行版都打不通，
  Web 进程能打通——这才是「边界机上的低权落地点可以进内网，分析机不行」的等价模型。
- **对 A1 的直接后果**：隧道的 `deploy` 走 SSH 会话（`server/intranet.go` 的 `intranetExec`），而 SSH 进去是
  root ⇒ 被自家规则拦住。要跑通「建隧道 → 经代理扫内网 → 回流 → 拆除」，必须把发起隧道的那个登录用户 uid
  加进 `JWLABINT` 白名单（或者改用 web uid 的会话执行）。这不是靶场的毛病，是测试设计上的真实约束，
  写用例时要显式处理。

**重建顺序（脚本是分段增量的，顺序错了就起不来）**：

```bash
# /root/lab-ubuntu 下，脚本里是 <REDIS_PASS> / <SVC_SSH_PASS> 占位符，跑之前用本机临时口令替换
./wslrun.sh Ubuntu-1 <(u1-netns.sh)        # 建拓扑（2026-11-04 已修：本脚本原来没 mkdir /opt/internal）
./wslrun.sh Ubuntu-1 <(u1-netns2.sh)       # 修正版拓扑：veth 语法以这份为准
./wslrun.sh Ubuntu-1 <(u1-netns-apps.sh)   # 段内应用（apt 装 redis、写 app.py、建单元）
./wslrun.sh Ubuntu-1 <(u1-netns3.sh)       # 修 FORWARD 段内互通与 redis 权限，重跑自检
systemctl restart jwlab-netns lab-intconsole lab-intredis lab-corepanel lab-coressh  # apps 写完文件后必须重启
```

踩过的三个坑：① `u1-netns.sh` 往 `/opt/internal` 写文件但 `mkdir` 只在后面的 apps 脚本里，
全新环境第一次必失败（已修）；② `ip link add <n> type netns <ns> name <n>` 这种写法在本机 iproute2 上报
`Garbage instead of arguments`，要用 `u1-netns2.sh` 里的 veth/peer 写法；③ 单元在 apps 脚本写文件**之前**
就被拉起，会留下 `active 但没监听` 的假健康，必须重启一次再自检。

**2026-11-04 交接时的状态**：`10.99.0.0/24` 段与 `jwint`(10.99.0.10)/`jwcore`(10.99.0.20) 已建，五个单元
`active`，`core-ssh22=open`、段内 `redis PONG`、Kali root 访问 `10.99.0.10:8000` 超时（隔离属性成立）；
但 `int-console` / `core-panel` 段内自检仍是 `000`（单元 active 却没有监听），**A1 的下一步就是查这两个
python 服务为什么没起**。靶机口令只在 `/tmp/.labredispw`、`/tmp/.labsvcpw`（600，用完删），不进任何文档与仓库。

## 7. 发布流程（谁做、按什么顺序）

1. 代码与文档改完 → 全量验证（并行 / 串行 / URI DSN / keyword DSN 四种口径，见开发手册 §4）；
2. 更新 `CHANGELOG.md`、`README.md`（**版本历史小节要同步**）、`.github/release-notes/vX.Y.Z.md`、
   `DEPLOY.md` 与 compose 的默认 tag、`web/package.json` 版本；
3. 敏感信息扫描 → 提交（**用 `git commit -F -` 配 heredoc**，消息里带引号会把 shell 命令搞炸，这是踩过的）；
4. `git push origin main` → 移动标签 `git tag -f vX.Y.Z` → `git push -f origin vX.Y.Z`；
5. 等 CI（8 个 job：prepare / frontend / binaries×2 / docker×2 / docker-publish / release）全绿；
6. 核对 Release 正文与三附件、GHCR 三个 tag 同 digest 且双架构；
7. 本地 `docker compose pull && docker compose up -d`，再做一次升级后验收（登录、两套壳存活检测、日志无 panic）。

**版本号策略**（已发生两次的决定，接手后照此办理）：文档/截图类改动可以移动 `vX.Y.Z` 标签重发；
